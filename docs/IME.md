## 1. 产品定位与核心动机

### 1.1 背景痛点
* **被动学习陷阱**：国内大量英语学习者处于“哑巴英语/输入瓶颈期”——看得懂、听得懂、会背单词与语法，但在日常生活中严重缺乏**主动输出（Active Production）**的机会。
* **高门槛对话工具的留存困境**：AI 口语伴侣或模拟对话 App（如 Speak、Toko）需要用户主动拿出大块意志力与时间去开启独立场景，使用摩擦力大，用户极易半途而废。
* **现有翻译输入法的“反向拐杖”效应**：搜狗、微信输入法等现有的“快捷翻译”是“输中文出英文”。这虽然便利了跨境工作者，但对学习者而言完全剥夺了英文思考的过程，学习者的大脑只负责产生中文。

### 1.2 核心理念：习惯叠加 (Habit Stacking) + 强制逆向输出
* **日常场景融合**：将英语输出练习嵌入到使用者全天候最高频的桌面行为——**打字输入**之中。
* **逆向输出范式**：**输入英/混杂文本，输出标准中文**。
  * 用户的大脑在想中文，但手指必须被迫构建英语表达；
  * 输入法将用户的草稿英语自动翻译纠偏为地道中文输出到目标应用（如微信、飞书、浏览器）；
  * 最终目标：随着熟练度提升，用户在大脑中形成“想表达意图 $\to$ 瞬间构建英文整句”的直觉本能。

## 2. 核心交互与产品形态

### 2.1 容错与无压输入体验
* 支持 **中英混杂**、**英语单词**、**全拼/简拼** 随意穿插。
* 例：输入 `wo today bushi very e, if you e, we go eat malatang.`
  * 目标聊天框实际接收：`我今天不是很饿，但如果你饿了的话，我们可以去吃麻辣烫。`
  * 输入法界面呈现：标准英文表达提示 `I'm not that hungry today, but if you're hungry, we can go get some Malatang.` 与关键语法点提示。

### 2.2 动态自愈界面 (Self-Healing UI)
摈弃传统输入法逐字翻页选字的交互，采用**整句预测与渐进坍缩**：
```
┌─────────────────────────────────────────────────────────────┐
│ 学习气泡 (Learning Bubble):                                 │
│ 💡 Did you mean: "I'm not that hungry today..." (not "bushi")│
├─────────────────────────────────────────────────────────────┤
│ 原始输入槽 (Input Track):                                   │
│ wo today bushi very e, if you e, we go eat malatang|        │
├─────────────────────────────────────────────────────────────┤
│ 最终输出中文预览 (Target Output - Enter 确认直接上屏):       │
│ 我今天不是很饿，但如果你饿了的话，我们可以去吃麻辣烫。       │
└─────────────────────────────────────────────────────────────┘
```
* **暂态文字 (Ghost Text)**：在输入初期，利用浅灰色文字呈现初级预测；随着后文锚点出现，前文预测自动无缝自愈纠错。
* **回车/空格落字**：按下确认键后，干净的标准中文直接填入宿主应用，学习提示气泡轻量淡出，不阻碍日常交流节奏。

## 3. 核心技术痛点与应对策略

### 3.1 同音拼音与语义歧义
* **痛点**：单字母拼音（如 `e`）候选极多（饿、恶、额、鹅等），规则词典若强行固化单一中文，极易误导后续大模型推理。
* **应对**：
  * **音意保留（Lattice 格子构建）**：前置阶段不替 AI 决定具体汉字，而是标注为概率节点 `[拼音: e | 候选: 饿, 恶, 额]`。
  * **英文锚点全局消歧**：利用整句中的英文实体（如 `eat`、`hungry`）通过大模型的 Attention（注意力机制）抑制无关项，自然收敛至“饿”。

### 3.2 键盘误触与双重拼写错误
* **痛点**：既有拼音混杂，又叠加英文打字手误（如 `todaey`、`malatnag`），造成状态空间指数级爆炸。
* **应对**：
  * **物理邻近加权编辑距离**：基于 QWERTY 键盘物理键位矩阵计算击键距离。相邻键（如 `r/t`）替换惩罚权重大幅低于远距离键（如 `p/t`）。
  * **极速前置过滤（SymSpell）**：利用 C++ 版 SymSpell 在 $<1\text{ms}$ 内完成英文与合法拼音的预归一化，把严重脏污数据清洗为带轻微瑕疵的浅度噪声数据。

## 4. 双流处理管线架构 (Dual-Stream Pipeline)

为了在保证毫秒级按键响应（不卡手）的前提下，实现整句深度语义推理，系统分为**快流**与**慢流**异步协同：

```
                用户击键事件 (Keypress Events)
                             │
                             ▼
                ┌─────────────────────────┐
                │ 1. 物理层邻近纠错       │ (QWERTY 距离矩阵)
                │ 2. 浅层词典分流过滤     │ (SymSpell + 拼音音节表)
                └────────────┬────────────┘
                             │
            ┌────────────────┴────────────────┐
            ▼                                 ▼
   【快流 Fast Path】                【慢流 Slow Path】
   • 引擎: 轻量 n-gram / C++词典     • 引擎: 本地大模型 (llama.cpp)
   • 延迟: < 15ms                    • 触发: 空格/标点/防抖(250ms)
   • 任务:                           • 延迟: 首字 ~100ms / 增量 ~40ms
     - 原始字符流即时跟随              • 任务:
     - 基础分词断句                      - 全局语法/语义消歧
     - 本地初级高频字呈现                - 英文地道改写 (Ghost Suggestion)
                                         - 最终精准中文生成
            │                                 │
            └────────────────┬────────────────┘
                             ▼
                  UI 动态自愈合并与渲染
```

### 延迟与算力预算指标 (桌面端 RTX 3060 / Apple Silicon 平台)
* **按键响应延迟**：$< 16\text{ms}$ (60 FPS 无感输入)
* **大模型首字延迟 (TTFT)**：$100\text{ms} \sim 250\text{ms}$
* **中文输出流生成耗时**：$200\text{ms} \sim 400\text{ms}$（约 10~20 tokens，用户按回车时基本已就绪）
* **英文分析提示渲染**：$0.8\text{s} \sim 1.5\text{s}$（后台异步淡入，不阻塞发送）

## 5. 技术选型与跨平台落地架构

整个输入法采用 **C/S 进程隔离架构**：底层系统注入壳极轻量，业务与 UI 运行于独立后台进程。

```
宿主应用进程 (WeChat, Word, Browser 等)
  └─ [平台原生轻量 Stub] (Windows TSF / Linux Fcitx5 / macOS IMK)
           │
           │ (低延迟 IPC: 共享内存 / 命名管道 / 本地 Socket)
           ▼
独立后台常驻进程 (Core Daemon)
  ├─ 界面层: Qt 6 (C++) + QML (无边框半透明悬浮窗 / 动画跟随)
  ├─ 纠错层: SymSpell C++ / 拼音 Trie 树
  └─ 推理层: llama.cpp (嵌入式 CMake 子模块, 支持 CUDA / Metal / Vulkan)
```

### 5.1 模块技术选型

| 架构层级 | 技术选型 | 说明 |
| :--- | :--- | :--- |
| **底层系统接入 (Hook)** | **Windows**: C++ TSF Stub DLL<br>**Linux**: Fcitx5 Addon (C++)<br>**macOS**: Swift/Obj-C IMKServer 包装 | 保持注入 Stub 小于 500KB，仅负责捕获原始击键与获取宿主光标绝对屏幕坐标 $(x, y)$。 |
| **GUI 与动效层** | **Qt 6 (C++) + QML** | 利用 `Qt::FramelessWindowHint` 与属性动画实现流式文字自愈与悬浮学习胶囊。 |
| **主控逻辑与并发** | **Qt C++ (Signals & Slots, QThreadPool)** | 确保 UI 主线程绝不执行任何耗时计算，推理与词典计算放入工作线程。 |
| **轻量拼写/分词** | **SymSpell (C++) + 拼音音节 Trie 树** | 原生运行在进程内存内，无额外语言绑定开销，微秒级匹配。 |
| **本地 AI 推理引擎** | **llama.cpp** | 直接作为 CMake 源码子模块链接到 Qt 项目，支持 GGUF 4-bit 量化，跨平台硬件加速。 |

## 6. 模型训练与微调策略

通用基础模型（如原始 Gemma-2-2B/9B）缺少对“中英拼音混杂 + 击键手误”场景的密集先验。必须通过轻量 LoRA 进行指令与抗噪微调。

### 6.1 噪声数据合成管线
1. **基础语料**：提取 100 万条高质量日常口语对话数据（中英对照）。
2. **加噪生成算子**：
   * **拼音化算子**：以 30% 概率随机将中文词替换为全拼或简拼（如 `不是` $\to$ `bushi` 或 `bs`）。
   * **键盘物理加噪**：按 QWERTY 键位距离随机对 10% 的字母进行临近替换、遗漏或顺序颠倒（如 `today` $\to$ `todaey`）。
   * **语序中文化算子**：将英文调整为带有典型 Chinglish 语序的结构。
3. **微调目标结构 (JSON Output)**：
   ```json
   {
     "target_zh": "我今天不是很饿，但如果你饿了的话，我们可以去吃麻辣烫。",
     "clean_en": "I'm not that hungry today, but if you're hungry, we can go get Malatang.",
     "critique": "Hungry 是形容词，应使用 'am not hungry' 而非 'bushi very e'。"
   }
   ```

## 7. 演进路线与阶段规划

### Phase 1: 算法与管道原型验证 (PoC)
* 搭建纯终端或简单界面工具。
* 跑通 `SymSpell (C++)` 快速纠错 + `llama.cpp (Gemma-2-2B-Q4)` 混杂输入解析。
* 验证增量 KV Cache 在连续打字状态下的推理延迟与显存占用表现。

### Phase 2: 桌面悬浮交互原型 (Qt/QML)
* 使用 Qt 6 构建常驻屏幕的输入状态悬浮窗。
* 实现输入槽、暂态纠错字符平滑动画、学习提示胶囊的 UI 渲染。
* 调优防抖 (Debounce) 与任务取消机制（用户继续打字时立即中断旧推理）。

### Phase 3: 系统输入法底层对接 (以单个操作系统切入)
* **首选路线 A (Linux)**：通过 Fcitx5 插件直接切入，开发门槛最低，调试环境友好。
* **首选路线 B (Windows)**：编写极简 TSF 代理 Stub，打通 IPC 命名管道，实现系统任意输入框的光标定位跟随与真实上屏。

### Phase 4: 领域微调与个人化自适应
* 训练并集成抗噪 LoRA 模型，将参数规模收敛至 2B~3B 级别。
* 引入用户个人生词本与高频词本地缓存，随使用时间越长，响应越快越精准。

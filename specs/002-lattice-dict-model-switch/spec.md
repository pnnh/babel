# Feature Specification: 拼音多候选格架构、真实词库与可切换本地模型

**Feature Branch**: `002-lattice-dict-model-switch`

**Created**: 2026-10-19

**Status**: Draft

**Input**: User description: "在 001-floating-ime-converter 已交付 MVP（全局热键浮窗、快流本地拼音纠错 FastCorrector、慢流本地 LLM 推理）基础上的实质性功能扩展。实测发现两个核心质量问题：① 内置拼音词典仅 14 条演示数据，常见词（如'烤肉''烧烤'）查无结果后退化为基于 QWERTY 键位邻近编辑距离的回退匹配，容易'宁滥勿缺'地产生错误匹配（如拼音 'chi'(吃) 因与 'shi'(是) 键位相邻、编辑距离低于阈值而被误配）；② FastCorrector 当前为每个拼音 token 只产出唯一候选字符串直接拼接后交给慢流 LLM，一旦唯一候选选错，错误信息已锁死进输入，LLM 即使很强也无法逆转语义（如同音字'吃/持/迟'选错后 LLM 已看不到原始拼音）。用户提出三个明确改进方向：（一）将 FastCorrector 的'单一候选'设计改为 Lattice 多候选格架构——为每个拼音 token 产出带权重的候选列表并排序，以某种形式传递给慢流 LLM 供其结合上下文消歧，这将改变 001 中 NormalizedCandidateText（单一候选字符串）及 qml-cpp-session-interface.md 中 rawInputSlotText、LlmEngine::generate() 输入参数等既有契约；（二）将拼音词典数据源从内置种子数据升级为基于 iDvel/rime-ice（雾凇拼音词库，GPLv3 许可，标准 Rime .dict.yaml 格式）的真实开源词库，需支持标准 Rime 词库格式解析、细胞词库（分类扩展词库）机制、同目录多文件自动合并加载，并考虑词库数据与程序版本解耦（用户可自行更新词库而无需重新编译）；GPLv3 许可随包分发可能触发的 copyleft 义务需明确记录为待用户/法务确认的开放问题；（三）推翻 001 FR-013 已确认的'固定单一 Qwen2.5-3B-Instruct GGUF Q4_K_M 模型'限制，改为浮窗右上角新增设置入口，可遍历约定本地模型目录并切换模型，按低配（沿用 Qwen2.5-3B-Instruct）/中配（16GB 级别主流桌面设备，具体型号待 research 阶段提出候选）/高配（Apple M1 Pro+32GB 统一内存 与 Windows+RTX 4090 24GB 显存两类基准硬件，可能为 Qwen2.5 14B 级别或 Gemma 系列 27B 级别 4-bit 量化版本）三档提供推荐模型。明确排除：模型自动下载、词库网络自动更新机制（除非澄清阶段另有决定）、候选字用户手动选择/人工干预上屏（除非澄清阶段决定纳入）。"

**语言（宪章《语言与文档规范》）**：用户故事、验收场景、功能需求、成功标准等说明性文字 MUST 使用简体中文；类名、路径、协议等技术标识可保留英文。

## 背景：基于 001 的基线与本次变更范围

本特性是对 `specs/001-floating-ime-converter`（已完成的跨平台浮窗转换器 MVP）的实质性扩展，而非从零开始的新系统。以下 001 已确立的契约继续作为本特性的既有基线，除非本 spec 后续条款明确声明取代：

- 浮窗三区域布局（原始输入槽 / 中文输出预览 / 学习提示气泡）、全局热键唤起与隐藏流程（001 FR-001/FR-002）。
- 快流本地纠错不依赖网络或大模型推理、目标端到端延迟低于 15 毫秒的性能约束（001 FR-003、SC-002）。
- 慢流防抖触发、生成状态迁移（`Idle → Debouncing → Generating → Ready/Stale`）与 `data-model.md` §3 `StandardOutputPreview` 的既有行为（001 FR-004/FR-005）。
- 确认/取消、剪贴板写入与模拟粘贴注入、Wayland 等环境下的统一"已复制到剪贴板，请手动粘贴"降级提示（001 FR-006～FR-009、FR-012）。
- 模型文件"用户手动下载后放置于约定本地目录、应用不随包分发、不提供应用内自动下载入口"的既有委派结论（`001/research.md` §7）。

## Clarifications

### Session 2026-10-19

- Q: iDvel/rime-ice 词库为 GPLv3 许可，随应用安装包一同分发该词库数据文件，是否接受由此可能触发的 copyleft 分发义务？ → A: 接受随包分发，履行 GPLv3 对应的 copyleft 义务（如源码可获得性声明、许可证文本附带等）。
- Q: 词库数据 MUST 与应用程序本体版本解耦，具体更新机制如何约定？ → A: 纯约定目录模式——用户自行将更新后的 `.dict.yaml` 词库文件放入本地约定目录，应用在启动或下一次加载时自动检测并生效，不提供应用内导入/更新界面。
- Q: 拼音多候选格信息传递给慢流 LLM 的具体形式？ → A: 结构化标注文本——`LlmEngine::generate()` 输入参数继续保持字符串类型，在字符串内部以约定的结构化标记标注各拼音位置的候选集合及权重，不改变参数类型为结构化数据对象。
- Q: 浮窗 QML 展示层是否需要向用户呈现某个拼音位置存在的多个候选及其权重？ → A: 不呈现给用户，维持 001 既有体验；但系统应在开发诊断用的控制台/日志中输出候选集合及权重信息，作为内部诊断能力辅助开发验证，不构成产品 UI 的一部分。
- Q: 中配档（约 16GB 级别主流桌面设备）与高配档（Apple M1 Pro+32GB 统一内存 / Windows+RTX 4090 24GB 显存）各自具体推荐模型是什么？ → A: 全系延续 Qwen 家族——中配 = Qwen2.5-14B-Instruct（GGUF Q4_K_M，约 9GB）；高配 = Qwen2.5-32B-Instruct（GGUF Q4_K_M，约 19.85GB）。选型依据：Qwen 系列中文训练语料占比更高，中文/拼音语境理解优于跨家族方案（如 Gemma2-27B-Instruct）；即使高配档在 RTX 4090 24GB（剩余约 4GB）与 M1 Pro 32GB 统一内存（剩余约 12GB）上内存余量相对紧张，仍判定为可行并优先于"余量更宽松但中文质量打折"的方案。Gemma2-27B-Instruct（GGUF Q4_K_M，约 17GB）保留为非并列呈现的备选方案，仅在后续实测发现 Qwen 系列高配档型号不可行时才重新评估启用。
- Q: 模型不可用时的提示文案与回退行为？ → A: 自动回退到此前可用的模型，并提示"模型 {当前不可用模型名称} 当前不可用，已自动切换回 {回退模型名称} 继续使用"；若回退目标也不可用则继续依次回退，直至低配默认模型 Qwen2.5-3B-Instruct 为止。
- Q: 用户在设置页面切换当前使用模型后，新模型是否需要重启应用或重新加载慢流推理引擎才能生效？ → A: 热切换但需重新加载推理引擎——应用程序本体（浮窗、热键、既有会话状态）无需重启，但慢流推理引擎需卸载旧模型、加载新模型，期间慢流功能可能暂不可用，加载完成后新模型生效。
- Q: 本特性验收所需达到的具体语义准确率提升幅度或目标阈值是多少？ → A: 设定绝对阈值 80%——语义正确样本比例 MUST 不低于 80%，高于 001 SC-007 的 60% 及格线，体现真实词库与 Lattice 多候选架构叠加的预期收益。

本 spec 明确**取代/修改**以下 001 既有契约，具体修改内容见下文 Functional Requirements：

- **001 FR-013**（"系统所依赖的本地大语言模型 MUST 为固定的 Qwen2.5-3B-Instruct GGUF Q4_K_M 单一模型"）——本特性推翻"固定单一模型"的限制，改为"默认模型 + 按硬件档位可切换"（见方向三 FR）。
- **001 `data-model.md` §1 `NormalizedCandidateText`**（"每个拼音位置仅承载单一候选字符串内容"的实体设计）——本特性要求改为可承载多候选、带权重的结构（见方向一 FR），具体字段结构不在本 spec 阶段规定，留待 `/speckit.plan`/`/speckit.tasks` 阶段设计。
- **001 `contracts/qml-cpp-session-interface.md`** 中 `rawInputSlotText` 属性当前"展示单一规整化候选文本"的语义，以及 `LlmEngine::generate()`（慢流推理入口）当前接收单一规整化字符串作为输入参数的既有假设——均需随方向一的多候选格架构调整，具体调整后的契约细节同样留待设计阶段确定。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 真实拼音词库消除因数据缺失导致的错误回退匹配 (Priority: P1)

用户在浮窗中输入包含常见现代汉语高频词拼音的草稿文本（例如背景中提到的"kaorou"烤肉、"shaokao"烧烤等日常生活词汇）。此前由于内置词典仅有 14 条演示性质的词条，这类常见词往往查无结果，系统被迫退化为基于键位邻近度的编辑距离回退匹配，容易产生"宁滥勿缺"的错误匹配结果。本特性交付后，系统的快流纠错基于真实、覆盖面更广的开源拼音词库数据，能够直接命中这类常见词的正确候选，不再因词典数据过于匮乏而频繁触发危险的回退路径。

**Why this priority**：这是当前最突出、最直接可感知的质量问题的根源之一——词典数据本身的匮乏。它不要求任何架构变更即可独立交付价值，且是方向一（Lattice 多候选架构）能够发挥效果的数据基础：候选集合的质量上限取决于词库是否收录了正确词条，若词库本身没有对应条目，再强的消歧架构也无法生成正确结果。因此将其列为优先级最高、风险最低、可独立验证的第一步。

**Independent Test**：收集一批此前因词典缺失而被错误回退匹配的典型拼音输入样本（如 kaorou、shaokao，以及背景中提到的 chi 被错配为 shi 的场景），在应用词库数据升级后重新输入这些样本，验证系统的快流纠错能够命中词库中的正确词条候选，不再退化为编辑距离回退匹配导致的错误结果。

**Acceptance Scenarios**:

1. **Given** 应用已加载基于真实开源拼音词库解析得到的词典数据，**When** 用户输入常见现代汉语高频词的拼音（如 kaorou、shaokao），**Then** 快流纠错结果命中词库中对应的真实词条候选，不再退化为纯编辑距离回退匹配。
2. **Given** 词库数据目录下存在按类别拆分的多个独立扩展词库文件（即细胞词库，如地名、成语、网络用语等分类词库），**When** 应用加载词典数据，**Then** 系统自动合并加载该目录下全部符合格式的词库文件中的词条，而不仅加载其中单一文件。
3. **Given** 用户获得了更新后的词库数据内容，**When** 用户按应用约定的方式使该内容对应用生效，**Then** 新增或变更的词条在后续快流纠错中生效，且该过程无需用户重新安装或升级应用程序本体。
4. **Given** 某拼音片段即便在扩充后的真实词库中仍然查无对应候选（如生僻自造词、超出词库覆盖范围的新词），**When** 系统执行快流纠错，**Then** 系统仍可回退到既有的编辑距离匹配作为兜底，不会因为查无候选而中断整个快流纠错流程。

### User Story 2 - Lattice 多候选格架构结合上下文消解同音字误判 (Priority: P2)

用户输入的拼音草稿中包含同音字歧义较高的片段（如 "chi" 对应"吃/持/迟/池/尺/齿"等多个合理候选）。在此之前，快流纠错会为该拼音片段锁定唯一一个候选字符串直接交给慢流大语言模型，一旦锁定的候选是错误的（如被误配为与上下文无关的其他字），错误已经写入慢流的输入文本中，慢流即便具备很强的语言理解能力也无法逆转这一错误，因为它已经看不到用户当初输入的原始拼音。本特性交付后，快流为每个拼音位置保留多个候选（而非仅锁定其中一个），并将这些候选连同权重信息一并提供给慢流，使慢流能够结合完整上下文语境进行候选消歧，最终给出与用户真实语义意图相符的标准中文译写结果。

**Why this priority**：这一方向建立在 User Story 1（真实词库）已扩充的候选数据基础之上——只有词库本身收录了正确候选，多候选架构才有意义去"从多个合理选项中挑出语境正确的那个"。它是比 User Story 1 更深层的架构变更，收益也更大（尤其在同音字歧义场景下），因此列为次优先级，建议在 User Story 1 交付之后实施。

**Independent Test**：构造一组已知在词库中能同时查到多个合理候选汉字/词语的拼音歧义测试样本（如 chi 对应吃/持/迟等），分别放入具备明确上下文语义线索、能指向其中某一特定候选的句子中输入，验证最终的标准中文译写结果所使用的汉字与上下文语义相符，而非被快流过早锁定的单一候选。

**Acceptance Scenarios**:

1. **Given** 用户输入的某个拼音片段在词库中可查到多个具有相近合理性的候选汉字/词语，**When** 快流完成纠错处理，**Then** 系统为该拼音位置保留多个候选（而非仅锁定其中一个）以供后续慢流阶段使用。
2. **Given** 某拼音位置存在多个候选，且用户输入的上下文具备足够语义线索指向其中一个候选，**When** 慢流完成标准中文生成，**Then** 最终输出的标准中文译写结果在该位置使用的汉字与上下文语义相符的候选一致。
3. **Given** 此前"唯一候选被过早锁定为错误字"的典型场景（如背景中"吃"被误配为"是"），**When** 用户输入相同或类似的拼音文本，**Then** 该类此前会被过早排除出候选集合的正确候选，在本特性交付后仍保留在候选集合中，使慢流具备基于上下文选中正确候选的机会。

### User Story 3 - 在设置页面按硬件配置水平切换本地慢流模型 (Priority: P3)

用户希望根据自己设备的硬件配置水平（如入门级轻薄本、16GB 级别主流台式机、或配备 Apple M1 Pro+32GB 统一内存/NVIDIA RTX 4090 24GB 显存的高性能设备），选择一个与自身硬件能力匹配、质量更优或资源占用更低的本地慢流推理模型，而不是被迫始终使用 001 中固定的单一默认模型。用户点击浮窗右上角新增的设置入口进入设置页面，该页面会遍历应用约定的本地模型目录，列出当前可用的模型文件供用户选择；用户选中某个模型后，后续的标准中文生成改为使用该模型。

**Why this priority**：这是独立于前两项质量改进之外的能力扩展——默认路径的核心行为（使用低配推荐模型）保持不变，用户是否使用该能力完全是可选的、锦上添花的体验升级，不影响核心转换闭环已验证的价值，因此优先级低于直接影响输出质量的前两项。

**Independent Test**：在浮窗界面中打开设置入口，验证能看到约定本地模型目录下所有可用模型文件的列表；选择其中一个与当前默认模型不同的模型后，验证后续触发的标准中文生成确实使用的是用户所选的模型，而非此前的默认模型。

**Acceptance Scenarios**:

1. **Given** 用户已唤起浮窗，**When** 用户点击浮窗右上角新增的设置入口，**Then** 系统展示设置页面。
2. **Given** 用户已在应用约定的本地模型目录中放置了一个或多个受支持格式的模型文件，**When** 用户进入设置页面，**Then** 系统列出该目录下所有被识别为可用模型的文件，供用户从中选择。
3. **Given** 设置页面已列出至少一个非默认的模型文件，**When** 用户选择该模型作为当前使用的模型，**Then** 系统无需重启应用程序本体即完成热切换：慢流推理引擎卸载旧模型并加载新模型（期间慢流功能可能短暂不可用），加载完成后后续触发的标准中文生成改为使用用户所选的新模型（见 FR-014）。
4. **Given** 用户此前选择的模型文件在约定目录下已被移除、损坏或无法再被加载，**When** 系统尝试使用该模型执行慢流推理，**Then** 系统以用户可理解的方式提示该模型当前不可用，复用 001 规格 FR-011 已确立的"不崩溃、不无响应"处理模式。

### Edge Cases

- 词库数据目录下存在格式错误、无法按 Rime `.dict.yaml` 规范解析的文件时，系统应如何处理（跳过该文件并提示、还是中断整个词库加载）？
- 同一词条在多个细胞词库文件中重复出现且权重取值不同时，系统应如何确定最终采用的权重/优先级？
- 某拼音位置的候选集合规模过大（常见同音字簇可达数十个）时，是否存在规模上限控制，以避免显著拖慢慢流推理耗时或使传递给慢流的信息过长？
- 设置页面列出的本地模型目录下存在无法被当前推理引擎识别或加载的文件（如文件损坏、量化格式不受支持）时，应如何向用户呈现？
- 用户在设置页面选择了明显超出自身设备硬件承载能力的高档位模型（如在低显存设备上选择高配档模型）时，系统应如何处理（阻止选择、运行时才报错提示、还是不作限制交由用户自行承担）？
- **许可证义务（已澄清，见 Clarifications）**：iDvel/rime-ice 词库采用 GPLv3 许可，应用 MUST 随安装包一同分发该词库数据文件，并 MUST 履行 GPLv3 对应的 copyleft 义务（包括但不限于：随包附带 GPLv3 许可证全文、保留原始版权与来源声明、确保该词库数据对应源码/数据内容的可获得性满足 GPLv3 分发条款要求）；具体履约方式的技术细节留待 `/speckit.plan` 设计阶段确定。

## Requirements *(mandatory)*

### Functional Requirements

**方向二：真实拼音词库**

- **FR-001**: 系统 MUST 使用基于真实开源拼音词库解析得到的词典数据作为快流纠错的主要数据来源，取代 001 中仅含 14 条演示性质词条的内置种子数据；词库 MUST 覆盖足够规模的现代汉语常见词汇，使本 spec 背景与 Edge Cases 中列举的典型常见词不再因词典缺失而被判定为查无候选并退化为编辑距离回退匹配。该词库数据文件 MUST 随应用安装包一同分发（见 Clarifications 会话 2026-10-19 对许可证问题的决定），分发时 MUST 履行 iDvel/rime-ice 词库所采用 GPLv3 许可对应的 copyleft 义务。
- **FR-002**: 系统 MUST 能够解析标准 Rime `.dict.yaml` 格式的词库文件，正确识别其 YAML frontmatter 元数据区，以及其后以制表符分隔的"词条、拼音、权重"数据行。
- **FR-003**: 系统 MUST 支持同一词库数据目录下存在多个独立的 `.dict.yaml` 文件（即 Rime 所称"细胞词库"，按类别拆分的扩展词库，如地名、成语、网络用语等分类词库）时，自动合并加载全部文件中的词条数据，而不仅加载其中单一文件。
- **FR-004**: 词库数据 MUST 与应用程序本体版本解耦：用户更新机制采用纯约定目录模式——用户自行将更新后的 `.dict.yaml` 词库文件放入应用约定的本地目录（替换既有文件或新增细胞词库文件均可），应用 MUST 在启动或下一次加载词库数据时自动检测该目录内容变化并生效，本特性范围内不提供应用内导入/更新界面。用户更新或替换词库数据内容后，新词条 MUST 在不重新编译、不重新安装应用程序本体的前提下生效。
- **FR-005**: 当某拼音片段在真实词库中确实查无对应候选（如生僻自造词、超出词库覆盖范围的新词）时，系统 MUST 保留既有的编辑距离回退匹配作为兜底，MUST NOT 因查无候选而完全中断快流纠错流程。

**方向一：Lattice 多候选格架构**

- **FR-006**: 系统 MUST 为原始输入中的每个拼音片段（或拼音 token）生成一个包含多个候选汉字/词语的候选集合，而非仅产出唯一一个候选字符串；候选集合中的每个候选 MUST 附带可用于排序/比较的权重信息，并按权重排序。此条 MUST 取代 001 `data-model.md` §1 `NormalizedCandidateText`"每个拼音位置仅承载单一候选字符串内容"的既有实体设计；具体替代后的数据结构字段定义不在本 spec 阶段规定，留待 `/speckit.plan` 设计阶段确定。
- **FR-007**: 系统 MUST 将各拼音位置的多候选集合连同其权重信息，以结构化标注文本的形式传递给慢流本地大语言模型：`LlmEngine::generate()` 的输入参数 MUST 继续保持字符串类型（不变更为结构化数据对象契约），但字符串内部 MUST 按约定的结构化标记格式，在每个拼音 token 位置标注其候选集合及各候选对应的权重信息，供慢流结合上下文语境进行候选消歧与最终标准中文生成；具体标记符号/排版细节不在本 spec 阶段规定，留待 `/speckit.plan` 设计阶段确定。此决策同步约束 001 `contracts/qml-cpp-session-interface.md` 中 `LlmEngine::generate()` 输入参数的调整方向——MUST 延续字符串类型，仅扩展字符串内容的组织形式。
- **FR-008**: 浮窗 QML 展示层（原始输入槽等区域）MUST NOT 因本特性引入的多候选格架构而向用户呈现候选集合及其权重，维持 001 既有体验——用户仅能看到最终的规整化展示/标准中文输出预览，不感知内部候选集合的存在。本条不含"用户手动选择/人工干预候选上屏"这一更复杂交互（该交互已在 Out of Scope 中明确排除）。系统 SHOULD 在开发诊断用的控制台/日志输出中记录各拼音位置的候选集合及对应权重信息，以辅助开发阶段验证 Lattice 多候选消歧效果；该日志输出属于内部诊断能力，不面向终端用户、不构成产品 UI 的一部分，具体日志格式留待 `/speckit.plan` 设计阶段确定。

**方向三：本地模型可切换**

- **FR-009**: 本需求 MUST 取代 001 规格 FR-013 中"系统所依赖的本地大语言模型 MUST 为固定的 Qwen2.5-3B-Instruct GGUF Q4_K_M 单一模型"这一限制性表述：Qwen2.5-3B-Instruct（GGUF Q4_K_M）由"系统唯一依赖的模型"降级为"默认模型，对应低配硬件档位推荐"，系统 MUST 支持使用该模型之外的其他本地模型文件。
- **FR-010**: 浮窗界面 MUST 新增一个设置入口（如按钮/图标），固定位于浮窗右上角，供用户点击后进入设置页面。
- **FR-011**: 设置页面 MUST 能够遍历应用约定的本地模型目录，列出该目录下所有被识别为受支持格式的模型文件，供用户从中选择一个作为当前慢流推理使用的模型。
- **FR-012**: 系统 MUST 提供按硬件配置水平分类的三档推荐模型信息（低配/中配/高配），供用户参考选择与自身设备匹配的模型进行下载。低配档 MUST 延续 001 规格 FR-013 已确认的 Qwen2.5-3B-Instruct（GGUF Q4_K_M），对应共享内存较小或无独立显卡的入门级桌面设备。中配档（对应约 16GB 级别显存/统一内存的主流桌面设备）MUST 推荐 Qwen2.5-14B-Instruct（GGUF Q4_K_M，模型体积约 9GB）。高配档（对应"Apple M1 Pro+32GB 统一内存"及"Windows+NVIDIA RTX 4090 24GB 显存"两类基准硬件）MUST 推荐 Qwen2.5-32B-Instruct（GGUF Q4_K_M，模型体积约 19.85GB）；选型依据：延续全系 Qwen 家族（与低配、中配同源），中文训练语料占比更高、在中文/拼音语境理解上表现更优，即便在 RTX 4090 24GB 显存（剩余约 4GB）与 M1 Pro 32GB 统一内存（剩余约 12GB）上余量相对紧张，仍判定为可行并优先于"余量更宽松但中文质量打折"的跨家族替代方案（如 Gemma2-27B-Instruct）。若后续实测发现 Qwen 系列在高配档缺少合适型号（如 32B Q4_K_M 版本实际不可行），Gemma2-27B-Instruct（GGUF Q4_K_M，约 17GB）MAY 作为备选方案被重新评估，但本特性当前阶段不将其作为并列候选呈现给用户。
- **FR-013**: 当用户在设置页面选择的模型文件变得不可用（缺失、损坏、无法加载）时，系统 MUST 复用 001 规格 FR-011 已确立的"以用户可理解方式提示、不崩溃、不无响应"处理模式：系统 MUST 自动回退到此前可用的模型（即用户当次会话中上一个成功加载并使用过的模型），并向用户提示"模型 {当前不可用模型名称} 当前不可用，已自动切换回 {回退模型名称} 继续使用"；若回退目标模型自身也不可用，MUST 依次继续回退，直至回退到低配默认模型 Qwen2.5-3B-Instruct（GGUF Q4_K_M）为止，确保慢流推理功能始终保持可用状态而非停滞等待用户干预。
- **FR-014**: 用户在设置页面切换当前使用模型后，系统 MUST 支持不重启应用程序本体的热切换：浮窗、全局热键、既有会话状态（原始输入槽内容、标准中文输出预览等）均 MUST 保持不受影响；但慢流本地大语言模型推理引擎 MUST 执行卸载旧模型、加载新模型的过程，该过程期间慢流功能 MAY 暂不可用（如触发生成请求时提示"模型加载中，请稍候"或类似可理解提示），加载完成后新模型生效并恢复慢流可用性。本条不要求达成"应用与推理引擎均无感、切换瞬时完成"的更高标准。
- **FR-015**: 模型文件的获取方式 MUST 延续 001 规格 `research.md` §7 已确立的委派结论：用户手动下载模型文件后放置于应用约定的本地目录，应用 MUST NOT 提供应用内自动下载模型文件的入口；本特性范围内不新增模型自动下载能力。

### Key Entities *(include if feature involves data)*

- **拼音候选格（Lattice Candidate Cell）**：描述原始输入中某一拼音片段（token）位置上保留的多个候选汉字/词语集合，每个候选携带可供排序/比较的权重信息；用于取代 001 中"每个拼音位置仅承载单一候选字符串"的 `NormalizedCandidateText` 设计。具体字段结构、与 QML 展示层及 `LlmEngine::generate()` 输入参数的最终对应关系，留待设计阶段按 FR-006～FR-008 的澄清结果确定。
- **真实拼音词库数据（Rime 格式词典）**：基于真实开源拼音词库（如 iDvel/rime-ice）、按标准 Rime `.dict.yaml` 格式组织的词条集合，可由同一目录下多个细胞词库文件合并构成；是快流纠错阶段候选来源的主数据，取代 001 中仅含 14 条词条的内置种子数据。
- **本地模型目录条目（Local Model Directory Entry）**：应用约定本地模型目录下，被设置页面遍历、识别到的每一个模型文件条目；可关联到硬件配置档位推荐（低配/中配/高配）及该档位对应的参数规模、量化精度等信息。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：在包含同音字歧义片段、以及此前因词库数据缺失而被错误回退匹配的高频常见词的真实测试语料集合上，用户确认采纳的最终标准中文译写结果中，语义正确（即与用户实际输入意图一致、无需额外人工修改其中因同音字/生僻词误判导致的错别字）的样本比例 MUST 不低于 80%（高于 001 SC-007 已确认的 60% 及格线，以体现真实词库与 Lattice 多候选架构两项质量改进措施的叠加预期收益），且相较本特性交付前的基线版本有可测量的提升。
- **SC-002**：用户可以完全在设置页面内（无需查阅额外文档或手动编辑配置文件）完成"从默认模型切换为约定本地模型目录下任意其他可用模型"这一操作。
- **SC-003**：针对背景中列举的低配（如共享内存较小的入门级设备）、中配（约 16GB 级别显存/统一内存的主流桌面设备）、高配（"Apple M1 Pro+32GB 统一内存"或"Windows+NVIDIA RTX 4090 24GB 显存"）三类硬件配置水平的用户，均能在设置页面的推荐信息中找到至少一个官方推荐、与自身硬件配置水平相匹配的可下载模型。
- **SC-004**：用户仅通过将更新后的词库文件放入应用约定的本地目录（见 FR-004 已确认的纯约定目录更新机制），即可使系统后续的快流纠错结果反映新增或变更的词条，而无需重新安装或升级应用程序本体。
- **SC-005**：在真实词库数据加载后，针对背景与 Edge Cases 中列举的常见生活化词汇样本，系统不再出现因词典缺失而退化为编辑距离回退匹配导致的错误候选锁定。

## Assumptions

- 本特性以 `specs/001-floating-ime-converter` 已交付的 MVP 为既有基线，复用其已确立的浮窗三区域布局、全局热键唤起、剪贴板写入与模拟粘贴注入等契约；除本 spec 背景章节明确声明取代/修改的条款外，001 既有 Functional Requirements、Success Criteria、Edge Cases 原样继续有效。
- iDvel/rime-ice 词库采用标准 Rime `.dict.yaml` 文件格式（YAML frontmatter 元数据 + 制表符分隔的"词条/拼音/权重"数据行），是用户本轮明确指定的数据来源（见背景章节 Input）。
- 低配档推荐模型沿用 001 规格 FR-013 已确认并经 `Clarifications` 锁定的 Qwen2.5-3B-Instruct（GGUF Q4_K_M），这是已存在的既有决策取值，非本特性新引入的默认猜测。
- 高配档所需兼容的两类基准硬件（"Apple M1 Pro 芯片+32GB 统一内存"与"Windows+NVIDIA RTX 4090 24GB 显存"）由用户在本轮明确给出，作为高配推荐模型选型需同时满足的硬件形态约束，非 Agent 自行推测。
- 模型文件的获取方式延续 001 规格 `research.md` §7 已有的委派结论（用户手动下载后放置于约定本地目录、应用不提供自动下载入口），本特性范围内不改变该结论。

## Out of Scope

- **模型文件的自动下载能力**：本特性不提供应用内自动从网络下载模型文件的功能；用户仍需手动下载模型文件后放置于应用约定的本地目录，延续 001 规格 `research.md` §7 已确立的委派结论。
- **词库数据的网络自动更新机制**：本特性不提供应用内检测新版本词库、自动联网下载并替换词库数据的功能，除非 `/speckit.clarify` 阶段另有决定。
- **候选字的用户手动选择/人工干预上屏**：本特性不在浮窗交互中提供"用户直接查看并手动点选某个拼音位置的候选字、人工决定最终上屏内容"这类更复杂的交互 UI，除非 `/speckit.clarify` 阶段决定纳入；Lattice 多候选信息的消费方仅限定为慢流本地大语言模型的内部消歧输入。
- **真正的系统级输入法框架接入、LoRA/模型微调、个性化学习记忆**等——延续 001 规格已确立的 Out of Scope 范围，本特性不改变该边界。

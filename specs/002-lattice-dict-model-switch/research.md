## 1. Rime `.dict.yaml` 格式实测核实（事实确认，非选型）

**背景**：为避免凭空假设格式细节，已直接拉取 `iDvel/rime-ice`（GitHub `main` 分支）仓库样本核实，而非仅凭用户描述。

**已核实事实**：

- 仓库 `LICENSE` 确认为 **GPL-3.0**（GitHub API `license.spdx_id = "GPL-3.0"`），与 spec Clarifications 的前提一致。
- `cn_dicts/base.dict.yaml` 实际结构：

  ```yaml
  # Rime dictionary
  # encoding: utf-8
  # ...（纯注释行，# 开头）
  ---
  name: base
  version: "2026-09-20"
  sort: by_weight
  ...
  # +_+
  啊啊	a a	27365
  啊啊啊	a a a	9820
  阿巴	a ba	999
  ```

  即：`---` 与 `...` 之间为 YAML frontmatter（本例仅 `name`/`version`/`sort` 三个简单标量字段）；`...` 之后为数据区，每行"词条 TAB 拼音（音节间以空格分隔）TAB 权重"，`#` 开头的行为注释，与 spec 描述一致。
- 顶层 `rime_ice.dict.yaml`（声明如何组合细胞词库的主词典）的 frontmatter **并非总是简单标量**，而是包含嵌套列表且列表项常见行内注释与被注释掉的行：

  ```yaml
  ---
  name: rime_ice
  version: "2026-01-26"
  import_tables:
    - cn_dicts/8105     # 字表
    # - cn_dicts/41448  # 大字表（按需启用）
    - cn_dicts/base     # 基础词库
    - cn_dicts/ext      # 扩展词库
    - cn_dicts/tencent  # 腾讯词向量（大词库，部署时间较长）
    - cn_dicts/others   # 一些杂项
  ...
  ```

  本特性 FR-003 采用"同目录多文件自动扫描合并"策略（不依赖 `import_tables` 声明本身来决定加载哪些文件），因此**不要求**正确解析 `import_tables` 的语义；但解析器扫描 frontmatter 边界（`---`/`...`）时仍必须能够正确跳过此类嵌套列表 + 行内注释而不误判 `...` 边界或崩溃，这是候选方案比较的关键风险点（见 §2）。
- `cn_dicts/` 目录体积参考（核实 GitHub 文件大小 API，供部署与解析性能预算参考，非本仓库实测）：`base.dict.yaml` ≈ 15.8MB、`ext.dict.yaml` ≈ 11.4MB、`tencent.dict.yaml` ≈ 16.5MB、`41448.dict.yaml` ≈ 378KB、`8105.dict.yaml` ≈ 113KB、`others.dict.yaml` ≈ 17KB，`cn_dicts/` 合计约 44MB 原始文本（不含仓库其余 `melt_eng.dict.yaml`/`radical_pinyin.dict.yaml` 等文件）。该体积量级用于评估 §2 候选方案的解析耗时与 sqlite3 导入耗时预算，MUST 在 `/speckit.tasks`/`/speckit.implement` 阶段以实际随包词库文件实测复核，本文件不代为断言具体加载耗时。
- 顶层 `rime_ice.dict.yaml` 在注释中给出了 Rime 原生引擎对"细胞词库间重复词条"的处理约定作为参考（非本特性拍板依据，仅记录行业既有约定供 §4.2 候选方案比较）："建议把扩展词库放到下面，有重复词条时，最上面的权重生效"——即 Rime 原生合并语义是"按 `import_tables` 声明顺序，越靠前的词库权重优先生效"。

**标记**：事实确认，不构成选型 Decision。

## 2. Rime `.dict.yaml` 解析方案选型（Decision）

**判定程序命中**：(d) 新增依赖（若引入第三方 YAML 库）。用户本轮任务指令仅要求"调研…给出候选方案与权衡"，**未**委派 Agent 代为选型，故本节按宪章原则 II/III 仅列候选，不拍板。

**候选方案**：

| # | 方案 | 优点 | 缺点 |
|---|------|------|------|
| 1 | 手写最小化解析器：仅识别 Rime `.dict.yaml` 已知结构——`---`/`...` 边界定位 frontmatter、frontmatter 内仅用简单的"顶层 `key: value`"与"跳过嵌套列表/注释直到下一个顶层 `key:` 或 `...`"的行级规则，不实现通用 YAML 语法（锚点、多文档、流式内联对象等） | 零新增依赖；无许可证顾虑；可精确贴合本特性"仅需识别 frontmatter 边界 + 制表符数据行"的实际需求（FR-002），不为用不到的通用 YAML 特性付出复杂度成本 | 正确性边界需靠单元测试样本（含真实 rime-ice 文件）覆盖，而非语言规范保证；若未来 rime-ice 上游 frontmatter 出现当前样本未覆盖的写法（如多行字符串、流式内联 `{}`/`[]`），存在解析失败风险，需要后续补丁跟进 |
| 2 | 引入 **yaml-cpp**（vcpkg 官方 port，MIT License，当前 vcpkg 版本约 0.9.0） | 通用 YAML 1.2 解析器，可正确处理 §1 观察到的嵌套列表、行内注释等任意 frontmatter 变体，无需为"未覆盖写法"持续打补丁；MIT 许可证与仓库既有依赖（`spdlog`/`sqlite3` 等宽松许可证）风格一致，vcpkg 官方 port 集成摩擦低 | 新增构建依赖；frontmatter 解析出的是通用 YAML 节点树，仍需额外代码把其中用到的字段（如未来若使用 `name`/`version`）映射为本特性结构；解析整份文件（含数万行数据区）若错误地交给 YAML 解析器而非仅解析 frontmatter 段，可能产生不必要的性能开销（需注意实现时仅对 `---`/`...` 之间的子串调用 yaml-cpp，数据区仍按制表符分隔逐行手工解析） |
| 3 | 引入 **ryml / rapidyaml**（vcpkg 官方 port 名 `ryml`，依赖 `c4core`，MIT License，号称零拷贝/高性能） | 同样可正确处理通用 YAML frontmatter；官方宣称解析性能优于 yaml-cpp，对 §1 提及的约 44MB 原始文本量级的整体加载耗时更友好（即便仅对 frontmatter 子串解析，整体依赖性能特性仍有余量） | 新增构建依赖（且多一层 `c4core` 传递依赖）；API 风格（零拷贝、基于 `csubstr`）与仓库现有 C++ 代码风格差异较大，引入与维护的学习成本高于 yaml-cpp；社区使用面小于 yaml-cpp，踩坑时可参考资料较少 |

**Recommendation（原文，非批准）**：若优先"零依赖、聚焦本特性实际需要的最小解析能力"，方案 1 更贴合——本特性对 YAML 的实际需求仅是"跳过 frontmatter 到 `...`"，不需要消费 frontmatter 内容本身（FR-002/FR-003 均只字未提需要读取 `name`/`version`/`import_tables` 等元数据用于产品行为），通用 YAML 解析器的大部分能力（锚点、多文档、tag 等）在本特性中用不上；若优先"面向 rime-ice 上游格式演进的长期健壮性、减少未来手工打补丁的维护负担"，方案 2（yaml-cpp）更稳妥，其许可证与集成成本均低于方案 3。暂不推荐方案 3，除非后续实测证实 frontmatter 解析/整体词库加载耗时确实构成瓶颈。

**最终选型（Decision，用户委派，Agent 采纳 Recommendation）**：采纳**方案 1——手写最小化解析器**。本节 Recommendation 本身给出两个条件分支（零依赖 vs 长期健壮性），Agent 在委派权限内选定"零依赖"分支，理由：① FR-002/FR-003 字面需求确认仅需"定位 `---`/`...` 边界并跳过"，方案 1 精确覆盖该需求，不引入用不到的能力；② 零新增构建依赖，避免 `vcpkg.json`/`CMakeLists.txt` 变更与跨平台（Windows/macOS/Linux）构建摩擦，与本计划在其余事项（§9 不持久化、§7.4 不新增硬件检测）中一贯采用的"最小必要修改"（宪章原则 V）取向保持一致；③ 方案 1 的健壮性风险（未覆盖写法）可通过单元测试样本（含 §1 已核实的 `rime_ice.dict.yaml` 嵌套列表 + 行内注释真实样本）缓解，属 `/speckit.tasks`/`/speckit.implement` 阶段可控的测试覆盖工作，不构成立即切换到有依赖方案的充分理由。实现落地 MUST 以 §1 已核实的真实 `rime_ice.dict.yaml`/`base.dict.yaml` 样本作为单元测试用例，覆盖"嵌套列表"“行内注释”“被注释掉的行”等已观察到的边界写法。

**标记**：~~`[NEEDS CLARIFICATION]`~~ → **已解决（用户本轮显式委派，Agent 采纳 Recommendation：方案 1 手写最小化解析器）**。

## 3. 真实词库分发与 GPLv3 Copyleft 履约技术方案

**委托依据**：spec Clarifications 已决定"接受随包分发，履行 GPLv3 对应的 copyleft 义务"；Edge Cases 原文："具体履约方式的技术细节留待 `/speckit.plan` 设计阶段确定"。本节设计履约的**技术落地步骤**，**不构成法律意见**，最终合规充分性判断超出本计划范围、建议另行法务复核。

**Decision**：

1. 随应用安装包分发的词库数据文件（`iDvel/rime-ice` 的 `.dict.yaml` 原始文本文件本身）**即视为 GPLv3 语境下的"源码"**——`.dict.yaml` 为人类可读、可直接编辑的纯文本格式（非编译产物），随包分发原始文件天然满足"源码可获得性"要求，不需要额外的"源码单独获取渠道"。
2. 在词库数据所在目录（见 §7/§9 的目录约定）旁随包附带：
   - `LICENSE-rime-ice.txt`：`iDvel/rime-ice` 仓库 `LICENSE` 文件的完整 GPLv3 许可证全文副本；
   - `NOTICE-rime-ice.txt`：记录数据来源（`https://github.com/iDvel/rime-ice`）、所采用许可证（GPL-3.0）、随包版本对应的上游 commit/tag（若上游后续更新，随本特性迭代同步更新该记录），以及原始版权声明摘录。
3. 应用关于页/文档（具体承载位置——沿用 001 既有 About/关于入口模式，若 001 尚无此类入口则属实现细节，由 `/speckit.tasks` 自主安排）中 SHOULD 提及"拼音词库数据来源于 iDvel/rime-ice（GPLv3）"，呼应 copyleft 对"保留原始版权与来源声明"的要求。

**理由**：上述三项均为 GPLv3 对"二进制/数据分发方"的典型履约模式（许可证全文随附、保留来源与版权声明、确保源码可得），且数据本身即为源码形式，技术实现成本低、不引入新的产品行为分支，未超出 spec Edge Cases 已委托的"技术细节"范围。

**标记**：~~`[NEEDS CLARIFICATION]`~~ → **已解决（spec 显式委托，Agent 设计落地步骤）**；最终法律合规性建议另行法务复核，不在本计划的"完成"定义内断言。

## 4. 词库目录加载的开放问题

### 4.1 词库目录下格式错误文件的处理策略（Decision）

**背景**：spec Edge Cases 原文："词库数据目录下存在格式错误、无法按 Rime `.dict.yaml` 规范解析的文件时，系统应如何处理（跳过该文件并提示、还是中断整个词库加载）？"——该问题**未**被转化为正式 FR 或 Clarification，属于会改变外部可观察行为（启动成败、日志/提示是否出现）的产品决策（判定程序 (a) 命中）。

**候选方案**：

| # | 方案 | 优点 | 缺点 |
|---|------|------|------|
| 1 | 跳过该文件，记录诊断日志，继续加载目录下其余文件 | 单个文件问题不影响整体可用性，贴合 FR-005"不应因查无候选而中断快流纠错流程"的整体精神 | 用户可能长期不知道某个细胞词库实际未生效（若无显著提示渠道） |
| 2 | 中断整个词库加载，回退到 `builtinSeedDictionary()` 兜底 | 行为保守、易于复现排查 | 一个文件损坏导致整批真实词库数据全部失效，与 FR-001 的"真实词库消除错误回退匹配"目标相悖，用户体验显著劣化 |
| 3 | 跳过该文件，仅写入诊断日志（不展示用户可见提示），与 FR-008 的"诊断日志不面向终端用户"风格保持一致 | 与本特性已确立的"候选/诊断信息仅开发可见"基调一致，不新增用户可见 UI | 若用户自行放置的词库文件长期被静默跳过，用户完全无从察觉 |

**Recommendation（原文，非批准）**：若优先"保证已确认的核心能力（真实词库消除错误回退）不因单点数据问题而整体失效"，方案 1/3 优于方案 2；方案 1 与方案 3 的区别仅在于是否存在用户可见提示，这进一步取决于"是否需要新增用户可见的词库加载状态提示 UI"——而 spec 并未要求本特性新增此类 UI（设置页面仅要求列出*模型*文件，未提及词库加载状态展示），故引入用户可见提示本身也需用户确认是否构成新增范围。

**最终选型（Decision，用户委派，Agent 采纳 Recommendation）**：采纳**方案 3——跳过该文件（不中断其余文件加载），仅写入开发诊断日志（`spdlog::debug`/`warn`，复用 §6 既定日志风格），不新增任何用户可见提示 UI**。理由：① Recommendation 已明确排除方案 2（与 FR-005"不应因查无候选而中断快流纠错流程"的整体精神相悖）；② 方案 1/3 的唯一差异是是否新增用户可见提示，而 spec 并未要求本特性新增词库加载状态展示 UI，按宪章原则 I（显式需求是唯一授权范围）与原则 V（最小必要修改），在无显式新增 UI 需求的情况下不引入新的用户可见提示面，故选方案 3 而非方案 1。落地要求：`RimeDictionarySourceFile.loadStatus` 在解析失败时取值 `Skipped`，并输出 `spdlog::warn("[RimeDictLoader] skip malformed file path={} reason={}", filePath, reason)` 一行诊断日志；目录下其余文件继续正常加载，应用启动/词库加载流程不中断。

**标记**：~~`[NEEDS CLARIFICATION]`~~ → **已解决（用户本轮显式委派，Agent 采纳 Recommendation：方案 3 跳过+仅诊断日志）**。

### 4.2 细胞词库间同词条重复、权重冲突的合并策略（Decision）

**背景**：spec Edge Cases 原文："同一词条在多个细胞词库文件中重复出现且权重取值不同时，系统应如何确定最终采用的权重/优先级？"——未转化为正式 FR，属判定程序 (a)/(b) 命中（影响最终候选排序结果，即影响 SC-001 语义正确率的客观统计结果）。

**候选方案**：

| # | 方案 | 优点 | 缺点 |
|---|------|------|------|
| 1 | 复用现有 `insertDictionaryEntries()` 的 `INSERT OR IGNORE`（`UNIQUE(surface_form, pinyin_full)`）语义：先加载的文件权重生效，后加载文件中的重复词条被忽略；加载顺序取**目录内文件名字典序** | 零代码改动（001 既有 sqlite3 schema 原样复用，见 `DictionarySchema.cpp`）；行为确定、可复现 | 文件名字典序与"预期优先级"无关联（如 `base.dict.yaml` 字典序先于 `tencent.dict.yaml`，纯属巧合而非刻意设计），用户新增细胞词库文件时无法直观预测自己的文件是否会覆盖既有权重 |
| 2 | 取重复词条的**权重最大值**生效（与加载顺序无关，须将 `INSERT OR IGNORE` 改为"存在则比较并取较大权重更新"） | 结果与文件加载顺序解耦，更符合"权重代表词频，取更可信的数值"的直觉 | 需要修改 `insertDictionaryEntries()` 的既有 SQL 语义（`INSERT OR IGNORE` → `INSERT ... | 3 | 参照 §1 核实的 Rime 原生引擎惯例——按**显式声明的优先级顺序**（而非文件名字典序）合并，优先级顺序需要一个新的配置来源（如本特性自行引入的"细胞词库加载顺序清单"文件，或沿用 rime-ice 自身 `rime_ice.dict.yaml` 的 `import_tables` 声明顺序） | 与 Rime 生态的既有约定对齐，用户若熟悉 Rime 可直接理解该行为 | 需要额外解析/维护一份"优先级声明"，且本特性 FR-003 已明确采用"同目录自动扫描合并"而非"按声明清单导入"，引入优先级声明清单某种程度上与"纯约定目录、免配置"的既定简化方向存在张力，需要重新评估是否与 FR-004"纯约定目录模式"的简洁性诉求冲突 |

**Recommendation（原文，非批准）**：方案 1 实现成本最低、可完全复用 001 既有 sqlite3 schema 行为，但"文件名字典序"的可预测性较弱；方案 2 在语义上更直觉，但需要修改既有 SQL 写入逻辑且"数值更大更可信"的假设本身未经验证；方案 3 更贴近 Rime 生态习惯，但与本特性"纯约定目录"的简化诉求存在张力，倾向不采纳。

**最终选型（Decision，用户委派，Agent 采纳 Recommendation）**：采纳**方案 1——复用既有 `insertDictionaryEntries()` 的 `INSERT OR IGNORE`（`UNIQUE(surface_form, pinyin_full)`）语义，按约定目录内文件名字典序加载，先加载文件中的权重生效，后加载文件中的重复词条被忽略**。理由：① Recommendation 已明确排除方案 3（与本特性"纯约定目录、自动扫描合并"的既定简化设计存在张力）；② 方案 1 与方案 2 相比零代码改动、完全复用 001 既有 sqlite3 schema 与既有实现（`babel/src/fastpath/DictionarySchema.cpp`），且方案 2"数值更大更可信"的假设本身未经验证（§1 已核实不同细胞词库的权重量纲/统计口径可能不可比），贸然引入"取最大值"反而可能产生无依据的排序结果；③ 符合本计划其余事项一贯的最小必要修改取向（宪章原则 V）。落地要求：`RimeDictLoader` 扫描目录时 MUST 按文件名字典序（`std::sort` 后的路径列表）依次调用 `insertDictionaryEntries()`，不引入额外的优先级声明清单。

**标记**：~~`[NEEDS CLARIFICATION]`~~ → **已解决（用户本轮显式委派，Agent 采纳 Recommendation：方案 1 文件名字典序 + `INSERT OR IGNORE`）**。

## 5. Lattice 多候选数据结构设计与慢流结构化标注文本格式

**委托依据**：spec FR-006/FR-007/FR-008 原文均明确"具体…留待 `/speckit.plan` 设计阶段确定"。

### 5.1 既有实现基础（事实核实，非选型）

- `babel::fastpath::PinyinTrie::queryByFullPinyin()`/`queryByAbbrev()`（`babel/src/fastpath/PinyinTrie.cpp`）内部已经维护"按 `frequencyWeight` 降序排序的候选列表"（`queryPrefix()` 内部 `std::sort` 后按 `maxResults` 截断），**但当前对外签名仅返回 `std::vector<std::string>`，在 `queryPrefix()` 返回前丢弃了权重数值**——这是实现 Lattice（FR-006 要求"每个候选 MUST 附带可用于排序/比较的权重信息"）必须修改的既有信号（返回类型需改为携带权重，如 `std::vector<std::pair<std::string, double>>`），记录于此供 `data-model.md`/`tasks.md` 引用来源。
- `babel::fastpath::FastCorrector::correctToken()`（`babel/src/fastpath/FastCorrector.cpp`）当前对 Trie 命中与编辑距离回退均只取"唯一最优候选"（`hits.front()` / 遍历整个词典仅保留 `bestDistance`/`best` 单值），这是 FR-006 要求取代的"单一候选"既有逻辑的具体位置。

### 5.2 Lattice 数据结构设计（Decision）

新增 `babel::fastpath::PinyinLattice`（`babel/src/fastpath/PinyinLattice.h`，详见 `data-model.md` §1），核心设计点：

- 以"格位（Cell）"为单位，一个格位对应原始输入中以空白分隔的一个 token（与现有 `correct()` 按空白分词的既有切分方式一致，不改变 FR-003 已确认的分词粒度）；
- 每个格位持有一个按权重降序排列的候选列表（候选来自 Trie 全拼命中 ∪ 简拼命中 ∪ 编辑距离回退候选的合并结果，而非仅取某一来源的最优解），取代 `correctToken()` 当前"任一来源命中即返回单值"的提前截断逻辑；
- 非拼音 token（已是中文/标点，`!looksLikeLatin()`）仍原样保留为"透传格位"（候选列表恒为该 token 自身的单一候选，权重 1.0），不引入歧义，保持与 FR-008"不引入候选集合"对这类格位的隐含预期一致。

### 5.3 结构化标注文本标记格式（Decision）

**格式提案**：

```
⟦原始token:候选1 权重1|候选2 权重2|...|候选N 权重N⟧
```

- 分隔符选用 `⟦`/`⟧`（U+27E6/U+27E7，数学双角括号）与 `|`：均为现代汉语文本与常见拼音输入中几乎不会自然出现的符号，便于 LLM 侧与后续若有需要的正则提取双向可靠识别，且不与 Qwen2.5 的 ChatML 特殊 token（`<|im_start|>` 等）冲突。
- **仅对候选数 ≥ 2（即存在真实歧义）的格位生成标注**；候选数为 1（含透传格位）的 token 直接以原样文本出现，不包裹标记——因为 FR-007 的字面诉求是"标注候选集合供慢流消歧"，对无歧义格位标注不产生消歧价值，反而显著增加 prompt 长度（§1 词库体量下常见词层面的无歧义 token 占多数）；该取舍落在 FR-007 已显式委托的"排版细节"范围内，不构成新的外部契约。
- 候选权重在标注前**按格位内部归一化**为两位小数的比例值（`weight_i / Σweight`），而非直接透出原始 `frequencyWeight`（真实词库中原始权重为任意量级整数，如 §1 示例中的 `27365`），避免大数值占用过多 prompt token 且对 LLM 不具有直接可比语义。
- 示例（对应背景中"吃"被误配为"是"的场景，设词库对 `chi` 返回候选"吃/持/迟/池/尺/齿"）：

  ```
  我⟦chi:吃 0.42|持 0.35|迟 0.15|池 0.05|尺 0.02|齿 0.01⟧了晚饭
  ```

- `LlmEngine::generate()` **输入参数类型保持 `QString` 不变**（符合 FR-007"MUST 延续字符串类型"的硬性约束），仅输入内容从"规整化后的单一候选字符串"变为上述标注文本；对应地，`LlmEngine.cpp` 内部的系统提示词（`kSystemPrompt`）需要补充一段说明本标注语法的文字，使 Qwen2.5-Instruct 能正确理解 `⟦⟧` 标注的含义并据此消歧（内部 prompt 工程细节，不改变 `generate()` 对外签名，按宪章原则 IV 单行记录）。

### 5.4 候选集合规模上限（Decision）

**背景**：spec Edge Cases 原文："某拼音位置的候选集合规模过大（常见同音字簇可达数十个）时，是否存在规模上限控制，以避免显著拖慢慢流推理耗时或使传递给慢流的信息过长？"——未转化为正式 FR，命中判定程序 (e)（显著影响 SC-003 延迟目标与 Prompt 长度/上下文窗口占用）。

**候选方案**：

| # | 方案 | 优点 | 缺点 |
|---|------|------|------|
| 1 | 不设上限，完整透出词库返回的全部候选 | 不丢失任何候选，理论上限消歧能力最强 | 极端同音字簇（如 `yi`/`ji`/`shi` 等常见音节在大词库下可能对应数十乃至上百候选）可能使单个格位的标注文本本身就超出合理 prompt 长度预算，拖慢慢流、挤占 `n_ctx=2048` 的有效上下文 |
| 2 | 每格位固定 Top-K（如 K=8）截断，取权重最高的 K 个 | 实现简单、prompt 长度上限可预测 | K 的具体取值本身即是一个需要依据数据与延迟预算调参的产品决策，当前无实测依据支撑任何具体数值 |
| 3 | 按"累计权重占比阈值"动态截断（如累计归一化权重达到 95% 即截断，不固定候选数量） | 对"候选分布集中"的格位（少数高权重候选即可覆盖）更紧凑，对"候选分布分散"的格位保留更多信息 | 实现复杂度高于固定 Top-K；阈值取值同样缺乏实测依据 |

**Recommendation（原文，非批准）**：在有实测数据（真实词库加载后，统计常见音节的候选数分布与对应 prompt 长度/延迟影响）之前，任何具体数值（K 值或阈值百分比）都将是缺乏依据的猜测；若必须给出一个起点用于后续实测调参，方案 2（固定 Top-K）实现与验证成本最低，便于后续按 SC-003 实测结果调整 K 值。

**最终选型（Decision，用户委派，Agent 采纳 Recommendation）**：采纳**方案 2——每格位固定 Top-K 截断**，起点取 **K = 8**（即每个歧义格位最多保留按 `rawWeight` 降序排列的前 8 个候选，归一化权重按截断后的子集重新计算）。理由：① Recommendation 明确方案 2 是"实测前起点"中成本最低、最易于后续调参的选择；② K=8 取自本节候选方案表中已给出的示例数值，覆盖常见同音字簇（如背景"吃"场景 6 个候选）仍有余量，同时对极端同音字簇（数十乃至上百候选）提供可预测的 prompt 长度上限；③ 该数值 MUST 在 `/speckit.implement` 阶段结合真实词库实测的候选数分布与 SC-003 延迟实测结果复核调整，本次选型仅提供可执行的初始实现值，不代为断言 8 为最终最优值。落地要求：`PinyinLattice` 构建阶段对每个格位的候选列表先按 `rawWeight` 降序排序，再截断至前 8 项，然后才计算 `normalizedWeight`（确保归一化基数为截断后的候选集合，而非截断前的全集）。

**标记**：~~`[NEEDS CLARIFICATION]`~~ → **已解决（用户本轮显式委派，Agent 采纳 Recommendation：方案 2 固定 Top-K，K=8，待实测调参）**。

## 7. 本地模型目录扫描与分档展示

### 7.1 目录扫描机制（Decision，内部细节）

沿用 001 `ModelPaths::conventionalModelDirectory()`（`babel/src/slowpath/ModelPaths.cpp`，既有 `QStandardPaths::AppDataLocation` + `/models` 约定）**原样作为本特性的多模型目录**——FR-011"遍历应用约定的本地模型目录"直接复用该既有目录常量，不新增第二个目录概念。新增 `babel::slowpath::ModelCatalog`（`data-model.md` §3）负责枚举该目录下所有 `*.gguf` 文件，构建 `ModelDescriptor` 列表（文件名、完整路径、文件体积、启发式档位标签）供设置页面消费。

**理由**：001 `ModelPaths` 已确立"约定本地目录、用户手动放置、不自动下载"的外部行为基线（`research.md` §7），本特性仅将"该目录下固定读取单一文件名"变为"该目录下枚举全部模型文件"，属于不改变已确立外部契约的内部实现扩展（宪章原则 II 引用来源：`babel/src/slowpath/ModelPaths.cpp`）。

### 7.2 档位标签启发式分类（Decision，内部细节）

`ModelDescriptor.tier` 按文件名关键字匹配（不区分大小写）：文件名包含 `3b`/`3-b` 归类 `Low`；包含 `14b` 归类 `Medium`；包含 `32b` 归类 `High`；均不匹配则归类 `Unknown`（用户自行放置的非推荐型号，仍可被选中使用，仅不参与"硬件档位推荐"展示分组，呼应 FR-012"供参考"而非强制限定可选范围）。此分类仅影响设置页面的展示分组文案，不影响候选是否可被选中/加载，属不改变外部行为之外的辅助展示细节（宪章原则 IV）。

### 7.3 设置页面对"无法加载模型文件"的呈现方式（Decision）

**背景**：spec Edge Cases 原文："设置页面列出的本地模型目录下存在无法被当前推理引擎识别或加载的文件（如文件损坏、量化格式不受支持）时，应如何向用户呈现？"——未转化为正式 FR，命中判定程序 (a)（UI 呈现方式即外部可观察行为）。

**候选方案**：

| # | 方案 | 优点 | 缺点 |
|---|------|------|------|
| 1 | 列表中不展示该文件（扫描阶段即尝试轻量校验，过滤掉明显无法加载的文件） | 用户看到的列表"选了就能用"，避免选中后才报错的挫败体验 | "轻量校验"能检测的问题有限（如 FR-011 Edge Case 提及的"量化格式不受支持"很多情况下只有真正加载时才能确定），可能产生"过滤不准确"（漏判/误判）问题 |
| 2 | 列表中正常展示该文件，用户选中并尝试切换时才报错，复用 FR-013 已确定的"自动回退+提示"链路 | 实现简单，直接复用 FR-013 既有的不可用处理路径，不需要额外的"预检测"逻辑 | 用户体验上需要"选了才知道不行"，与 User Story 3 Edge Case 关注的"应如何呈现"诉求（暗示希望有更早的呈现区分）存在落差 |
| 3 | 列表中展示该文件但附加"不可用"视觉标记（如置灰/图标），仍允许选中以触发 FR-013 的回退提示 | 兼顾"信息透明"（用户知道该文件存在但可能有问题）与"实现简单"（复用 FR-013 回退链路，不需要事先准确判定"能否加载"） | 判定"附加不可用标记"的具体依据（文件大小异常/扩展名不符/完整性校验）本身仍需定义，若依据过于粗糙可能显示误导性的"不可用"标记 |

**Recommendation（原文，非批准）**：方案 3 在"透明度"与"实现复杂度"间相对折中，但其"标记依据"仍需进一步定义才能落地，不构成可直接执行的确定方案。

**最终选型（Decision，用户委派，Agent 采纳 Recommendation）**：采纳**方案 3——列表中展示该文件但附加"不可用"视觉标记（置灰/图标），仍允许选中以触发 FR-013 既有回退+提示链路**。Recommendation 指出该方案的"标记依据"本身未定义，Agent 在委派权限内补充定义如下，使方案 3 成为可直接执行的确定方案：

- **标记依据**：`ModelCatalog::scan()` 枚举目录时，对每个候选文件做一次轻量、零额外依赖的文件头校验——读取文件前 4 字节，判断是否等于 GGUF 文件格式的魔数 `"GGUF"`（`0x47 0x47 0x55 0x46`）。
  - 校验失败（文件过短、头 4 字节不匹配，如文件损坏/非 GGUF 格式）→ `ModelDescriptor.availability = KnownUnloadable`，设置页面对该条目附加"不可用"视觉标记（置灰 + 提示图标），**仍可被选中**，选中后按既有 `switchModel()` 流程尝试加载并按 FR-013 触发回退提示。
  - 校验通过（头 4 字节匹配）→ `ModelDescriptor.availability = Unverified`，不附加标记，正常展示；真正被选中尝试加载后，加载成功则更新为 `Verified`，加载失败（如量化格式不受当前引擎版本支持等头部校验无法检测的问题）则更新为 `KnownUnloadable` 并对后续展示追加标记。
- **理由**：该校验仅为读取本地文件头 4 字节的轻量操作，不新增跨平台 API/第三方依赖，不改变"真正是否可加载"仍以实际加载结果为准的既定事实（即未过度承诺"轻量校验=绝对准确"，头部匹配但仍加载失败的情况被 `Verified`/`KnownUnloadable` 的事后更新机制覆盖），与方案 3 "信息透明 + 实现简单"的初衷一致，同时满足 Recommendation 指出的"标记依据需进一步定义"的缺口。

**标记**：~~`[NEEDS CLARIFICATION]`~~ → **已解决（用户本轮显式委派，Agent 采纳 Recommendation：方案 3，并补充定义标记依据为 GGUF 文件头魔数校验）**。

### 7.4 用户选择超出硬件能力档位模型时的限制策略（Decision）

**背景**：spec Edge Cases 原文："用户在设置页面选择了明显超出自身设备硬件承载能力的高档位模型…系统应如何处理（阻止选择、运行时才报错提示、还是不作限制交由用户自行承担）？"——未转化为正式 FR，命中判定程序 (a)。

**候选方案**（原文已在 Edge Cases 列出三选项雏形，本节补充权衡）：

| # | 方案 | 优点 | 缺点 |
|---|------|------|------|
| 1 | 阻止选择（设置页面事先检测设备内存/显存，低于档位所需阈值的选项禁止点选） | 提前拦截明显会失败的操作 | 需要新增"设备硬件能力检测"能力（跨平台获取可用内存/显存，macOS 统一内存与独立显卡 VRAM 的检测方式/API 均不同），引入 spec 未提及的新技术能力面，超出当前 FR-011/FR-012 字面范围 |
| 2 | 不作限制，交由用户自行承担（选择后若加载失败，复用 FR-013 已确定的自动回退+提示链路） | 零新增检测逻辑，完全复用已确定的 FR-013 行为，实现成本最低 | 用户可能在不知情下多次尝试明显不可行的档位，体验上依赖"事后提示"而非"事先提醒" |
| 3 | 不阻止选择，但在推荐信息旁追加"仅供参考，实际是否可加载取决于设备剩余可用内存/显存"等提示文案，选择后行为与方案 2 相同 | 兼顾"不新增检测技术能力"与"管理用户预期"，实现成本接近方案 2 | 提示文案本身是否需要用户确认具体措辞，仍是一项（较小的）产品文案决策 |

**Recommendation（原文，非批准）**：方案 2/3 均不引入 spec 未授权的跨平台硬件检测新能力，成本显著低于方案 1；二者差异仅在于是否追加一句说明性文案。

**最终选型（Decision，用户委派，Agent 采纳 Recommendation）**：采纳**方案 2——不作限制，交由用户自行承担选择，选择后若加载失败则完全复用 FR-013 已确定的自动回退+提示链路，不新增任何形式的硬件能力检测或额外说明性文案**。理由：① Recommendation 已排除方案 1（引入 spec 未授权的跨平台硬件检测新技术能力，超出 FR-011/FR-012 字面范围）；② 方案 2 与方案 3 的唯一差异是是否追加说明性文案，而该文案本身的具体措辞 Recommendation 原文亦指出"仍是一项（较小的）产品文案决策"——按宪章原则 I（显式需求是唯一授权范围）与原则 V（最小必要修改），在无进一步文案决策授权的情况下，选择零新增的方案 2，不产生额外的待决留白；③ 与 §4.1（不新增用户可见提示）、§9（不新增持久化机制）保持一致的最小必要修改取向。落地要求：设置页面模型列表不对任何档位做选择前拦截，三档推荐信息（`RecommendedModelProfile`）展示为 spec FR-012 已锁定的固定文字内容，不追加硬件适配性提示；`switchModel()` 对任意已选中文件一视同仁地尝试加载，失败路径完全复用既有 FR-013 回退链路。

**标记**：~~`[NEEDS CLARIFICATION]`~~ → **已解决（用户本轮显式委派，Agent 采纳 Recommendation：方案 2 不限制+复用 FR-013 回退链路）**。

## 8. 模型热切换与并发安全设计（Decision，内部细节）

**背景衔接**：本仓库工作树中 `babel/src/slowpath/DebounceScheduler.{h,cpp}` 已记录"llama_context 非线程安全，不可并发 decode"的既有教训（`m_generationInFlight` 守卫，防止同一 `LlmEngine` 实例被重叠触发第二次 `generate()`）。FR-014 的热切换在此基础上新增一个此前不存在的风险：**切换过程中可能正有一个 `generate()` 调用正在另一线程上运行**（见 `SessionController::onSlowPathTriggered()` 当前实现——`generate()` 在 detached `std::thread` 上执行，持有裸指针 `LlmEngine *engine = m_llmEngine.get()`）；若此时 `switchModel()` 释放旧 `LlmEngine`（析构触发 `llama_free`/`llama_model_free`），该裸指针将悬空，构成 use-after-free。

**Decision**：

1. `SessionController` 持有 `m_llmEngine` 的类型由 `std::unique_ptr<LlmEngine>` 改为 `std::shared_ptr<LlmEngine>`；`onSlowPathTriggered()` 启动后台线程时，向线程 lambda 按值捕获一份 `shared_ptr` 拷贝（而非裸指针），使该 `LlmEngine` 实例的生命周期由"是否仍有引用持有"决定，而非由 `SessionController` 成员变量的存续单独决定。
2. `switchModel(path)` 的执行步骤：① 置位 `m_modelSwitching = true`（新增只读属性，供 QML 展示"模型加载中，请稍候"，对应 FR-014）；② 在**非 UI 线程**构造新的 `LlmEngine` 实例（模型加载本身是重 I/O+计算操作，避免阻塞 UI 线程，与现有 `generate()` 的后台线程模式一致）；③ 加载完成后，通过 `QMetaObject::invokeMethod(..., Qt::QueuedConnection)` 回到 UI 线程，将 `m_llmEngine` 替换为新实例（旧 `shared_ptr` 引用计数递减；若此刻仍有在飞的 `generate()` 调用持有旧实例的拷贝，旧实例会在该调用返回、其线程 lambda 结束后才真正析构，不会在"仍被使用中"时被提前销毁）；④ 置位 `m_modelSwitching = false`，发出 `modelAvailableChanged`/新增 `currentModelChanged` 信号。
3. 若新模型加载失败（`modelAvailable() == false`），按 FR-013 执行级联回退：依次尝试"此前可用的模型"（`SessionController` 新增运行时栈/列表记录"本次应用运行期间已知可成功加载的模型路径"，见 `data-model.md` §4），直至低配默认模型 `ModelPaths::conventionalModelFilePath()` 为止；每次回退均按上述①–④流程执行，并通过新增信号携带提示文案"模型 {当前不可用模型名称} 当前不可用，已自动切换回 {回退模型名称} 继续使用"（FR-013 原文文案）。

**理由**：`shared_ptr` 方案是 C++ 标准库内即可实现的最小改动并发安全手段，不引入新依赖；与现有 `onSlowPathTriggered()` 的"后台线程执行推理、`QueuedConnection` 回传主线程"既有模式完全一致，仅将裸指针捕获改为 `shared_ptr` 值捕获，属不改变外部可观察行为的内部实现强化（宪章原则 IV）。

**标记**：~~`[NEEDS CLARIFICATION]`~~ → **已解决（内部细节，Agent 自主决定）**。

## 9. 模型选择运行时状态与跨应用重启持久化（Decision）

**背景**：spec FR-014 仅定义"同一次应用运行期间"的热切换语义（应用本体不重启），**未提及**用户切换后的选择是否需要在应用下次启动时被记住（即是否需要将"当前选中模型路径"持久化到磁盘配置文件，而非仅存于进程内存）。这并非 spec 遗留的 Edge Case 原文问题，而是本次设计 `data-model.md` 所需的"当前选中模型持久化状态"实体时新发现的未决项——命中判定程序 (a)（直接决定"重新打开应用后是否沿用上次选择"这一用户可感知行为）。

**候选方案**：

| # | 方案 | 优点 | 缺点 |
|---|------|------|------|
| 1 | 不持久化：每次应用启动固定使用低配默认模型（`ModelPaths::conventionalModelFilePath()`），用户需在每次启动后的新会话中重新于设置页面选择 | 零新增持久化机制；行为与 001 既有"固定默认模型启动"完全兼容，只是允许会话内切换 | 若用户的设备明确偏好中/高配模型，每次启动都要重新手动切换，体验上不够"记住用户偏好" |
| 2 | 持久化到本地配置文件（如 `QSettings`，Qt 既有能力，无新增依赖），应用启动时读取并尝试加载上次选中模型，失败则按 FR-013 回退链路降级 | 用户偏好得以保留，体验更连贯 | 新增一个磁盘配置文件/存储位置（纵使使用 Qt 既有 `QSettings` 无新依赖，仍是新增的持久化行为本身，需要明确其存储路径、写入时机、是否受本特性之外的配置管理约束） |

**Recommendation（原文，非批准）**：若严格以"本特性 spec 字面仅要求会话内热切换"为边界，方案 1 更贴合最小必要修改原则（宪章原则 V）；若用户的真实预期包含"记住选择"，需显式确认后方案 2 才能视为已授权范围内的工作。

**最终选型（Decision，用户委派，Agent 采纳 Recommendation）**：采纳**方案 1——不持久化**，每次应用启动固定使用低配默认模型（`ModelPaths::conventionalModelFilePath()`），用户需在每次启动后的新会话中按需重新于设置页面选择；该选择在本次应用运行期间持续有效，直至应用退出。理由：① Recommendation 明确指出在无显式确认"记住选择"属于已授权范围的情况下，方案 1 更贴合最小必要修改原则（宪章原则 V），而用户本轮委派仅要求"按 Recommendation 执行"，并未额外提出"需要记住选择"的新诉求，不构成方案 2 所需的"显式确认"；② 与 spec FR-014 字面仅要求"同一次应用运行期间"热切换完全一致，不隐含扩大范围；③ 零新增持久化机制，`data-model.md` §8 `ActiveModelRuntimeState` "纯进程内存状态"的既有设计保持不变，无需改动。

**标记**：~~`[NEEDS CLARIFICATION]`~~ → **已解决（用户本轮显式委派，Agent 采纳 Recommendation：方案 1 不持久化，`data-model.md` 中相应实体按"运行时内存状态"设计已直接吻合该最终选型）**。

## 10. 高配档 Qwen2.5-32B-Instruct 在目标硬件上的可行性验证方法

**边界声明**：本节**仅设计验证方法/步骤**，**不断言** Qwen2.5-32B-Instruct Q4_K_M 在 M1 Pro 32GB 统一内存 / RTX 4090 24GB 显存上必然满足 SC-003 延迟目标——spec Clarifications 已将"选用该型号"本身确定为既定决策（FR-012），但其**实测延迟是否达标**是一个需要在 `/speckit.implement` 阶段以真实硬件实测验证的经验问题，`/speckit.plan` 阶段 MUST NOT 代为断言。

**已核对的社区参考数据（非本仓库实测，仅供预估/制定验证预算参考）**：

- RTX 4090（24GB 显存）：公开社区基准显示 Qwen2.5-32B 系列 Q4_K_M 量化、llama.cpp + CUDA 后端下，生成速度参考值约 **40+ tokens/s**，显存占用约 19GB（24GB 显存下有约 4–5GB 余量，与 spec Clarifications 中"剩余约 4GB"的预估一致）。
- Apple M1 Pro（32GB 统一内存）：公开社区基准显示 30B 级别模型 Q4_K_M 量化、llama.cpp + Metal 后端下，生成速度参考值约 **4–8 tokens/s**，显著低于独立显卡方案；该区间跨度较大，受提示词长度/上下文占用影响明显。

**验证步骤设计（Decision，方法论本身属内部测试细节）**：

1. 在真实目标硬件（M1 Pro 32GB 实机 / RTX 4090 24GB 实机）上分别部署 Qwen2.5-32B-Instruct GGUF Q4_K_M，使用与 001 `LlmEngine` 相同的加载路径（`llama_model_load_from_file` + `llama_init_from_model`，macOS 保持 `n_gpu_layers = 999` 启用 Metal；Windows/Linux+CUDA 场景需确认 `vcpkg.json` 的 `llama-cpp` overlay port 是否需要新增 `cuda` feature——**此为新增依赖/构建配置变更，命中判定程序 (d)**，不在本阶段自行决定是否启用，留待 `/speckit.tasks` 按 §12 一并确认）。
2. 使用 §5.3 设计的结构化标注文本格式构造与 quickstart.md 验证场景一致的典型输入（含多格位歧义、不同串长度），实测首批内容延迟与整句生成完毕延迟，对照 SC-003 既有阈值（首批 <300ms、整句 <800ms，继承自 001 FR-013 对应的 SC-003，本特性未修改该阈值数值本身）。
3. 若实测不达标，按 spec Clarifications 已写明的既定预案处理：**不在本特性内更换高配档推荐模型**（Gemma2-27B-Instruct 仅作为"后续实测不可行时才重新评估"的非并列备选，重新评估本身需要新一轮决策，不在本计划自动触发）；仅如实记录实测结果，供后续决策参考。
4. 验证结果（通过/不通过、具体延迟数值）记入 `/speckit.implement` 阶段的任务验收记录（而非本 `research.md`，因本文件产出于实测之前，不能预写尚未发生的实测结论）。

**标记**：方法论本身为 **Decision**（内部测试步骤设计，不改变外部契约）；`cuda` feature 等新增依赖/构建配置事项若需启用，在 §12 一并列为待确认项。

## 11. 设置页面 UI 技术方案（Decision）

**委托依据**：用户本轮任务指令原话——"规划阶段决定具体是独立 Window 还是同一 Window 内的视图切换，这是实现细节可自主决定，不需要打断用户确认，除非改变外部可观察行为"。

**Decision**：采用**同一 `FloatingWindow` 内的视图切换**（而非新开一个独立 QML `Window`），具体为在 `FloatingWindow.qml` 内新增一个 `StackView`（或等价的 `visible` 条件切换容器），默认展示现有三段式主视图，点击浮窗右上角新增的设置按钮后切换到新增的 `SettingsPanel.qml` 视图，设置页面内提供"返回"操作切回主视图。

**理由**：
- FR-010 仅要求"固定位于浮窗右上角的设置入口"与"点击后进入设置页面"，未要求该页面必须是独立顶层窗口；采用同一 Window 内视图切换可以完整复用 001 已确立的无边框浮窗、置顶、窗口管理器行为（`Qt.FramelessWindowHint | Qt.Tool | Qt.WindowStaysOnTopHint`），避免引入"第二个独立窗口的焦点归属、与 `TargetFocusContext` 捕获时机的潜在交互"等 001 未曾处理过的新问题面。
- 对外可观察行为（"点击右上角按钮能进入设置页面，页面内能看到模型列表并完成选择"）与"独立 Window"方案完全等价，故本决策落在用户本轮已委派的"不改变外部可观察行为"范围内。

**标记**：~~`[NEEDS CLARIFICATION]`~~ → **已解决（用户本轮显式委派，Agent 实际选择：同一 Window 视图切换）**。

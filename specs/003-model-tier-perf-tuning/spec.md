# Feature Specification: 模型档位调整、GBNF 语法约束解码与防抖节奏优化

**Feature Branch**: `003-model-tier-perf-tuning`

**Created**: 2026-10-19

**Status**: Draft

**Input**: User description: "在 002-lattice-dict-model-switch（真实词库 + Lattice 多候选 + 本地模型可切换）已交付基础上的后续性能优化扩展。实测发现：低配 Qwen2.5-3B 满足 001 SC-003 延迟阈值但本次抽测翻译语义有误；中配 Qwen2.5-14B 延迟超出 SC-003 阈值约 3.2 倍但语义正确；高配 Qwen2.5-32B 外推延迟约 6.7 秒。用户与 Agent 讨论后确定四个改进方向：（一）将中配推荐从 Qwen2.5-14B-Instruct 调整为 Qwen2.5-7B-Instruct、高配从 Qwen2.5-32B-Instruct 调整为 Qwen2.5-14B-Instruct，仅调整推荐档位对应的具体模型数值，不改变三档结构本身；（二）投机解码（Speculative Decoding）——工程量较大（需同时维护草稿模型与目标模型两个 llama_context 实例及调度逻辑），仅作为已识别改进方向记录在案，本特性不实施，留待后续专项 spec；（三）引入 llama.cpp 原生支持的 GBNF 语法约束解码，使 LlmEngine::generate() 的生成结果从语法层面强制排除 Lattice 标注符号（⟦、⟧、|）泄漏到最终上屏文本的可能性，不改变 generate() 对外签名与既有 QML↔C++ 契约；（四）DebounceScheduler 的防抖窗口从固定 200 毫秒改为依据当前选定模型档位动态调整（非默认中/高配档位拉长），以降低持续输入时被频繁打断触发重复整句生成的体验割裂感，不改变既有状态机本身。涉及产品层决策分歧之处（防抖窗口具体数值与分档规则、GBNF 合法字符集边界、语法梗阻回退行为）须标记 NEEDS CLARIFICATION，不得自行拍板。"

## 背景：基于 001/002 的基线与本次变更范围

本特性是对 `specs/001-floating-ime-converter`（浮窗转换器 MVP）与 `specs/002-lattice-dict-model-switch`（真实词库 + Lattice 多候选 + 本地模型可切换）两项已交付特性的后续性能优化扩展，而非从零开始的新系统。以下既有契约继续作为本特性基线，除非本 spec 后续条款明确声明取代：

- 001 FR-004/FR-005、SC-003：慢流防抖触发、生成状态迁移（`Idle → Debouncing → Generating → Ready/Stale`），以及"首批内容延迟 < 300 毫秒、整句生成延迟 < 800 毫秒"的性能阈值。
- 002 Clarifications（2026-10-19 对 001 SC-003 的交叉修订）：SC-003 的延迟阈值**仅对低配默认模型（Qwen2.5-3B-Instruct）强制适用**；用户主动切换为中/高配模型视为已知情地以更长延迟换取更高翻译质量，MUST NOT 要求中/高配模型满足该阈值。
- 002 FR-006～FR-008：Lattice 多候选格架构、`LlmEngine::generate()` 以结构化标注文本（`⟦候选1 权重1|候选2 权重2|...⟧`）传递候选信息给慢流模型的既有契约。
- 002 FR-009～FR-015：本地模型可切换的三档结构（低配/中配/高配）、设置页面模型目录扫描、热切换、模型不可用自动回退链路。

**实测数据背景**（本机 Apple M1 Pro，同一测试样例）：低配 Qwen2.5-3B 生成耗时 628ms（满足 SC-003，但本次抽测存在语义误译）；中配 Qwen2.5-14B 生成耗时 2579ms（超出 SC-003 阈值约 3.2 倍，语义正确）；高配 Qwen2.5-32B 未实测，按参数量外推预估约 6.7 秒。该组数据是本特性四个改进方向的共同触发依据。

本 spec 明确**取代/修改**以下 001/002 既有条款，具体修改内容见下文 Functional Requirements：

- **002 FR-012**（中配推荐 Qwen2.5-14B-Instruct、高配推荐 Qwen2.5-32B-Instruct 的具体型号数值）——本特性调整为中配 Qwen2.5-7B-Instruct、高配 Qwen2.5-14B-Instruct（见方向一 FR），三档结构本身与 002 其余条款不变。
- **001 `DebounceScheduler` 固定 200 毫秒防抖窗口**（001 FR-004/FR-005 实现中的既有常量取值）——本特性要求该数值依据当前选定模型档位动态变化（见方向四 FR），既有状态机迁移逻辑不变。
- **`LlmEngine::generate()` 当前仅依赖系统提示词"建议性"约束标注符号不泄漏**的既有实现方式——本特性要求引入语法层面的强制约束（见方向三 FR），`generate()` 对外签名与 QML↔C++ 契约不变。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 中配/高配档位用户的实际使用延迟体感改善 (Priority: P1)

用户此前在设置页面将慢流模型切换为中配或高配档位，以换取比低配默认模型更高的翻译语义质量。但按 002 原有推荐数值（中配 Qwen2.5-14B、高配 Qwen2.5-32B），实测/外推延迟远超 001 SC-003 原定阈值数倍，且 001 持续沿用的固定 200 毫秒防抖窗口会让用户在持续输入时频繁触发整句重新生成，每次触发都伴随数秒等待，造成"越用越高配、体验越割裂"的观感。本特性交付后，用户在设置页面看到的中配/高配推荐模型数值调整为延迟代价更低的档位（中配 Qwen2.5-7B-Instruct、高配 Qwen2.5-14B-Instruct），且选用非默认档位后防抖窗口随之拉长，减少持续输入过程中因短暂停顿被误判为"输入完成"而触发的重复整句生成次数，用户整体感知到的交互节奏更连贯、等待体验更可预期。

**Why this priority**：这是本特性四个方向中唯一直接改善"当前已上线、用户正在实际使用的中/高配档位"延迟体感的用户可感知价值，且方向一（模型数值调整）与方向四（防抖节奏调整）需协同配合才能完整体现效果——仅调整模型数值不改变防抖频率，仅调整防抖窗口不降低单次生成耗时，两者叠加才是本特性对该用户群体的核心交付价值，故列为最高优先级。

**Independent Test**：在设置页面分别切换为调整后的中配、高配推荐模型，重复执行此前导致 002 中配档位 2579ms 延迟实测的测试样例，验证新档位的实测生成延迟相较原 002 档位数值有可测量的降低；同时在持续输入场景下（连续击键、间隔短暂停顿）比较防抖窗口调整前后触发"整句重新生成"的次数，验证非默认档位下触发次数相较固定 200 毫秒基线有可测量的减少。

**Acceptance Scenarios**:

1. **Given** 用户已唤起设置页面，**When** 用户查看中配/高配推荐模型信息，**Then** 系统展示的推荐型号为调整后的数值（中配 Qwen2.5-7B-Instruct、高配 Qwen2.5-14B-Instruct），而非 002 原有的 Qwen2.5-14B-Instruct/Qwen2.5-32B-Instruct。
2. **Given** 用户已切换为调整后的中配或高配模型，**When** 用户输入一段草稿文本触发慢流生成，**Then** 实测整句生成延迟相较 002 原对应档位的实测/外推数值有可测量的降低。
3. **Given** 用户当前选定的模型档位为中配或高配（非默认低配），**When** 用户持续输入且中途出现短暂停顿，**Then** 系统使用的防抖窗口时长相较低配默认档位的既有数值更长，减少因短暂停顿被误判为"输入完成"而触发的整句重新生成次数。
4. **Given** 用户将当前模型档位切换回低配默认档位，**When** 用户继续输入，**Then** 防抖窗口恢复为 001 已确立的既有数值，不受本特性调整影响。
5. **Given** 此前用户已按 002 旧版推荐数值手动下载并放置 Qwen2.5-32B-Instruct 或 Qwen2.5-14B-Instruct 模型文件于约定本地目录，**When** 用户进入设置页面，**Then** 该文件仍可被扫描识别并供用户手动选择使用，不因推荐档位数值调整而从模型目录中消失或被禁止选用，仅不再作为官方默认推荐项展示。

### User Story 2 - 最终上屏文本不再可能包含 Lattice 标注符号残留 (Priority: P2)

用户使用浮窗完成一次标准中文转换确认并上屏。此前系统仅通过系统提示词以自然语言方式"建议"模型不要把 Lattice 内部候选标注符号（`⟦`、`⟧`、`|`）带入最终输出，这种约束是建议性而非强制性的，理论上仍存在模型未遵循提示、把标注符号残留在生成结果中并最终被用户确认上屏的风险。本特性交付后，系统在慢流推理层面引入语法层面的强制约束，使生成结果从结构上不可能包含这些标注符号，用户确认上屏的标准中文文本始终是不含任何内部标注痕迹的纯净文本。

**Why this priority**：这是一项正确性/质量保障类改进，修复的是既有实现中"建议性约束不保证生效"的潜在缺陷，重要性仅次于直接影响延迟体感的方向一+四组合（已有真实实测数据佐证其影响面与紧迫性更高），但仍是本特性范围内与用户可感知结果直接相关的交付项，故列为次优先级。

**Independent Test**：构造多组已知容易触发多候选歧义标注（即慢流输入文本中包含 `⟦...|...⟧` 结构化标注片段较多）的测试样例，在引入语法约束前后分别执行慢流生成，验证语法约束引入后的生成结果中不出现 `⟦`、`⟧`、`|` 字符，且该结论对该测试语料集合的覆盖样本全部成立（而非此前依赖提示词时的"大概率不出现"）。

**Acceptance Scenarios**:

1. **Given** 慢流输入文本中包含多个拼音位置的结构化候选标注（`⟦候选1 权重1|候选2 权重2|...⟧`），**When** 慢流本地大语言模型执行生成，**Then** 生成结果中不出现 `⟦`、`⟧`、`|` 这三个标注符号。
2. **Given** 用户对慢流生成的标准中文输出预览按下回车确认，**When** 内容被写入系统剪贴板并尝试模拟粘贴，**Then** 最终出现在目标应用中的文本不含任何 Lattice 内部标注符号残留。
3. **Given** `LlmEngine::generate()` 已引入语法约束采样，**When** 该方法被 `SessionController` 等既有调用方调用，**Then** 其对外签名（输入输出均为 `QString`）与 001/002 已确立的 QML↔C++ 会话契约保持不变，调用方代码无需因本特性而修改。

### Edge Cases

- 此前基于 002 旧版推荐数值已下载 Qwen2.5-14B-Instruct/Qwen2.5-32B-Instruct 的用户，在本特性调整推荐档位数值后，其模型目录条目的档位标签（如仍标注"中配"/"高配"，还是改为"自定义"/"非推荐"等）具体如何呈现，留待 `/speckit.plan` 设计阶段按 FR-004 的既有决定（该文件仍可被扫描识别并使用）具体设计展示细节，不改变"仍可使用"这一已决定的行为本身。
- 用户在中配/高配档位下持续快速输入、几乎不出现停顿时，拉长后的防抖窗口是否会让"首批内容"展示相较此前更晚才出现：该场景不违反既有基线，因 001 SC-003 的 300ms/800ms 阈值按 002 Clarifications 已确认仅对低配默认模型强制适用，中/高配档位用户已知情地以更长延迟换取更高质量，本特性对此不新增强制阈值。
- 当 GBNF 语法约束导致模型在某一生成步骤找不到任何语法规则允许的合法延续 token（生成梗阻）时，按 FR-008（2026-10-19 澄清）系统 MUST 提前终止生成并直接输出梗阻点之前已生成的部分内容，不放宽约束续写、不判定为整体失败、不强制要求用户重试。
- 语法约束所认定的"合法输出字符集"边界已按 FR-007（2026-10-19 澄清）采用最宽边界（汉字/中文标点/数字/英文字母/全半角标点/emoji 均合法，仅强制排除 `⟦`、`⟧`、`|` 三个标注符号），不再误伐翻译结果中本应合法出现的品牌名、技术缩写等内容。

## Requirements *(mandatory)*

### Functional Requirements

**方向一：调整中配/高配推荐模型数值**

- **FR-001**: 系统 MUST 将设置页面展示的"中配"推荐模型由 Qwen2.5-14B-Instruct（GGUF Q4_K_M）调整为 Qwen2.5-7B-Instruct（GGUF Q4_K_M），取代 002 规格 FR-012 对应条款中的中配型号数值。
- **FR-002**: 系统 MUST 将设置页面展示的"高配"推荐模型由 Qwen2.5-32B-Instruct（GGUF Q4_K_M）调整为 Qwen2.5-14B-Instruct（GGUF Q4_K_M），取代 002 规格 FR-012 对应条款中的高配型号数值。
- **FR-003**: 本次调整 MUST NOT 改变 002 已确立的"低配/中配/高配"三档推荐结构本身、本地模型目录扫描/识别机制、用户手动选择切换机制、模型不可用自动回退链路（002 FR-009～FR-015）等既有行为；调整范围严格限定为"推荐档位对应的具体模型名称/文件名常量"这一单项内容。
- **FR-004**: 此前基于 002 旧版推荐数值已被用户手动下载并放置于应用约定本地模型目录的 Qwen2.5-14B-Instruct、Qwen2.5-32B-Instruct 等模型文件，系统 MUST 仍将其识别为可用模型并允许用户在设置页面手动选择使用，MUST NOT 因本次推荐档位数值调整而将其从模型目录扫描结果中排除或阻止加载；该类模型仅不再作为官方默认推荐项展示。

**方向二：投机解码——已识别但本特性不实施的改进方向**

> 本小节仅作记录，**不**转化为本特性的功能需求（FR），**不**纳入本特性的用户故事/验收标准，**不**因本记录而产生任何本特性内的实现预期。

- **背景**：当前慢流推理为逐 token 标准自回归解码，每个 token 均需完整执行一次目标模型的前向计算，是中/高配档位延迟偏高的根本原因之一。
- **方向描述**：投机解码（Speculative Decoding）通过引入一个参数规模更小、速度更快的"草稿模型"预测多个候选 token，再由目标模型一次性批量验证，命中时可免去目标模型对已验证 token 的逐一前向计算，从而无损加速生成过程。
- **预期收益**：llama.cpp 原生支持该机制；公开资料显示典型提速幅度约 1.5～3 倍，2 倍较为常见；由于验证阶段仍确保与目标模型单独解码结果等价，预期不损失翻译语义质量。
- **工程复杂度评估**：需要同时维护草稿模型与目标模型两个独立的 `llama_context` 推理实例（而非当前单一 `LlmEngine` 内部单一 `llama_context` 的既有设计），并新增草稿生成-批量验证的调度逻辑，涉及对 `LlmEngine` 内部推理管线的结构性改造，工程量显著大于本特性其余三个方向。
- **结论**：本特性不实施该方向，留待后续单独立项的专项 spec 评估与交付。

**方向三：GBNF 语法约束解码**

- **FR-005**: 系统 MUST 在慢流本地大语言模型推理过程中引入 llama.cpp 原生支持的 GBNF 语法约束采样，使生成过程中的每一个 token 均受语法规则约束，从语法层面强制排除 Lattice 内部候选标注符号（`⟦`、`⟧`、`|`）出现在最终生成文本中的可能性；此为对 002 FR-007 中"避免标注符号泄漏"既有意图的强化落实——002 FR-007 当前仅通过系统提示词的自然语言"建议性"约束实现该意图，本特性将其强化为语法层面的强制约束。
- **FR-006**: 该语法约束能力 MUST 仅作为 `LlmEngine` 的内部推理实现细节引入，MUST NOT 改变 `LlmEngine::generate()` 的对外签名（输入输出均为 `QString`），MUST NOT 改变 001/002 已确立的 QML↔C++ 会话契约（`contracts/qml-cpp-session-interface.md`）。
- **FR-007**: 语法约束所认定的"合法输出字符集"MUST 采用最宽边界：常用汉字、中文标点、阿拉伯数字、英文字母（覆盖品牌名/技术缩写等合法混排内容，如"iPhone""GPT"）、全角/半角标点、emoji 均视为合法输出字符；GBNF 语法规则 MUST 仅强制排除 `⟦`、`⟧`、`|` 三个 Lattice 内部标注符号本身，MUST NOT 额外收窄其余字符类别，以避免误伐翻译结果中本应合法出现的内容（2026-10-19 澄清，见 Clarifications）。
- **FR-008**: 当语法约束导致模型在某一生成步骤找不到任何语法规则允许的合法延续 token（生成梗阻）时，系统 MUST 提前终止该次生成，直接将梗阻点之前已生成的部分内容作为本次生成结果；系统 MUST NOT 放宽或移除语法约束继续生成剩余部分，MUST NOT 将该情况判定为整体生成失败或强制要求用户重试（2026-10-19 澄清，见 Clarifications）。
- **FR-009**: 系统 SHOULD 利用语法约束对合法输出空间的收窄效果，降低模型生成解释性前后缀或其他"啰嗦"内容的倾向，预期可能间接缩短生成文本长度、降低整句生成延迟；本 spec MUST NOT 在规格阶段断言具体缩短幅度或延迟降低的数值，相关收益 MUST 在 research/实现阶段完成后以实测数据记录。

**方向四：模型档位相关的防抖窗口动态调整**

- **FR-010**: 系统 MUST 支持 `DebounceScheduler` 的防抖窗口时长依据用户当前选定的慢流模型档位（低配/中配/高配）动态变化，取代 001 中固定 200 毫秒常量的既有实现方式。
- **FR-011**: 当用户选定模型为低配默认档位（Qwen2.5-3B-Instruct）时，防抖窗口 MUST 保持 001 已确立的既有数值（200 毫秒）不变，本特性 MUST NOT 影响低配默认档位用户已验证过的交互节奏。
- **FR-012**: 当用户选定模型为中配档位（Qwen2.5-7B-Instruct）时，防抖窗口 MUST 拉长至 500 毫秒；当用户选定模型为高配档位（Qwen2.5-14B-Instruct）时，防抖窗口 MUST 拉长至 800 毫秒；中配与高配 MUST 分别按各自档位设定独立数值，MUST NOT 采用"所有非默认档位统一同一拉长值"的方案（2026-10-19 澄清，见 Clarifications）。
- **FR-013**: 本特性 MUST NOT 改变 `DebounceScheduler` 既有状态机本身（`Idle → Debouncing → Generating → Ready/Stale` 迁移逻辑、`m_generationInFlight` 并发保护守卫等 001/002 已确立行为逻辑），调整范围严格限定为"防抖窗口时长"这一个参数的取值来源——从固定常量变为依赖当前选定模型档位的可变值。
- **FR-014**: 当用户在设置页面切换模型档位（触发 002 FR-014 已确立的模型热切换）导致防抖窗口数值随之变化时，该变化 MUST 在当次模型热切换完成后的下一次防抖触发周期生效，MUST NOT 要求重启应用程序本体或浮窗会话。

### Key Entities *(include if feature involves data)*

- **模型档位防抖参数（Tier Debounce Profile）**：描述"模型档位 → 对应防抖窗口时长"的映射关系，取代 001 中"防抖窗口为固定单一常量"的既有设计；按 FR-011/FR-012（2026-10-19 澄清）为每档位独立配置：低配 200 毫秒、中配 500 毫秒、高配 800 毫秒。具体字段结构（是否为简单枚举映射等实现形式）留待 `/speckit.plan` 设计阶段定义。
- **GBNF 输出语法规则（Output Grammar Rule）**：描述约束 `LlmEngine` 生成采样的语法定义，合法输出字符集边界（FR-007）与生成梗阻回退行为（FR-008）已于 2026-10-19 澄清确定；具体 GBNF 语法文件/规则表达方式留待 `/speckit.plan` 设计阶段定义。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：用户在设置页面切换为调整后的中配推荐模型（Qwen2.5-7B-Instruct）后，针对本特性背景中列举的实测测试样例，整句生成延迟相较 002 原中配档位（Qwen2.5-14B-Instruct）实测的 2579 毫秒有可测量的降低。
- **SC-002**：用户在设置页面切换为调整后的高配推荐模型（Qwen2.5-14B-Instruct）后，针对同一实测测试样例，整句生成延迟相较 002 原高配档位（Qwen2.5-32B-Instruct）外推的约 6.7 秒有可测量的降低。
- **SC-003**：中配档位（防抖窗口 500 毫秒）/高配档位（防抖窗口 800 毫秒）用户在持续输入（连续击键、间隔短暂停顿）场景下，因防抖触发导致的"整句重新生成"次数，相较固定 200 毫秒防抖窗口的既有基线有可测量的降低，主观反馈"打字时被频繁打断"的体验割裂感减少。
- **SC-004**：在覆盖同音字歧义/多候选标注场景的测试语料集合上，用户确认并最终上屏的标准中文文本中，不出现任何 Lattice 内部标注符号（`⟦`、`⟧`、`|`）残留，该结论对测试语料集合的验证通过率达到 100%。
- **SC-005**：低配默认档位用户的既有延迟体验（001 SC-003 的 300 毫秒/800 毫秒阈值）与既有防抖交互节奏（200 毫秒窗口）在本特性交付后保持与 001/002 交付时一致，不受本特性影响。

## Assumptions

- 本特性以 `specs/001-floating-ime-converter` 与 `specs/002-lattice-dict-model-switch` 已交付的能力为既有基线；除本 spec 背景章节明确声明取代/修改的条款外，001/002 既有 Functional Requirements、Success Criteria、Edge Cases 原样继续有效。
- 本特性背景中列举的实测数据（低配 628ms、中配 2579ms）与外推数据（高配约 6.7 秒），以及"参数量与延迟近似线性缩放"的工程判断依据（据此估算 7B 约 1.46 秒），均为用户在本轮提供的既有事实/工程判断，非 Agent 自行推测；新调整后的中配（7B）/高配（14B）档位的具体延迟数值仍需在 research/实现阶段重新实测，本 spec 不对新档位数值做强约束性断言。
- Qwen2.5-32B-Instruct 不再作为官方"高配"默认推荐项，但用户仍可自行将其手动放入本地模型目录并选用，该既有能力不受本特性影响（见 FR-004），这是用户在本轮背景中明确给出的决定，非 Agent 自行推测的默认值。
- llama.cpp 已原生支持 GBNF 语法约束采样能力，是方向三可行性的技术前提，由用户在本轮背景中明确指出，非 Agent 自行调研得出的假设。
- 投机解码所需的"同时维护草稿模型与目标模型两个 `llama_context` 实例、草稿-验证调度逻辑"的工程复杂度评估，是用户与 Agent 此前讨论达成的既有共识结论，本 spec 仅记录该结论作为"本特性不实施"的依据，不再重新评估其可行性或收益数值。
- 002 已确立的 GPLv3 词库分发义务、Lattice 多候选格架构、模型目录扫描/识别/热切换/自动回退等机制，均作为既有基线在本特性范围内保持不变。

## Out of Scope

- **投机解码（Speculative Decoding）的实际工程实现**：已在上文"方向二"专门小节记录为已识别的改进方向及其预期收益、工程复杂度评估，本特性不交付任何草稿模型维护、双 `llama_context` 调度相关的代码或设计，留待后续单独立项的专项 spec。
- **Qwen2.5-32B-Instruct（或其他非本次新推荐数值的旧档位模型）官方推荐地位的移除之外的处理**：本特性仅将其移出"官方默认推荐"展示，不涉及对该类已下载模型文件的删除、迁移提示、兼容性校验等额外处理（具体展示细节见 Edge Cases）。
- **002 已确立的 Lattice 多候选格架构、真实拼音词库解析、语义准确率阈值（002 SC-001 的 80% 基线）本身的进一步优化**：本特性不改变上述机制与既有阈值，仅在其基础上做本 spec 列出的四个方向的针对性调整；GBNF 语法约束预期不降低既有语义准确率，但本特性不设定更高的新语义准确率验收阈值。
- **`DebounceScheduler` 既有状态机、并发保护逻辑本身的重新设计**：本特性仅调整"防抖窗口时长"这一个参数的取值来源，不改变 `Idle → Debouncing → Generating → Ready/Stale` 状态迁移逻辑或既有并发保护守卫。

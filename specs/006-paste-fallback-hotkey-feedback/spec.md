## Clarifications

### Session 2026-10-21

- Q: 目标窗口在浮窗唤起期间被切换/最小化/关闭后（含判断结果不确定的情形），按确认键时系统应如何处理——统一降级为与 001 FR-012 一致的"已复制到剪贴板，请手动粘贴"提示（不新增差异化文案），还是仍尝试执行模拟粘贴操作（接受内容可能被注入到当前实际前台的某个无关窗口这一风险）？ → A: 统一降级为与 001 FR-012 一致的"已复制到剪贴板，请手动粘贴"提示，不新增差异化文案；系统 MUST NOT 在该场景下仍尝试执行模拟粘贴操作。
- Q: 热键注册失败时的提示承载方式——当前应用没有任何常驻于系统托盘/菜单栏的 UI，且热键注册失败场景下浮窗本身也无法通过热键唤起（经核实，`main.cpp`/`Main.qml` 中也不存在 Dock 图标点击、托盘菜单或命令行二次唤起等任何旁路，浮窗在此场景下确实不可达），是否需要新增一个独立于浮窗之外的常驻提示载体（如系统托盘图标），还是采用操作系统级一次性系统通知？ → A: 采用操作系统级系统通知作为提示承载方式。
- Q: 该提示的触发时机——应在应用启动检测到热键注册失败后立即呈现，还是应在用户实际尝试使用（按下热键但无反应）之后才被动呈现？ → A: 应用启动检测到热键注册失败后立即呈现（复用现有 `bootstrapPlatformDefaults()` 中已存在的失败判断分支同步触发该系统通知），不等待用户实际尝试使用。

### Session 2026-10-21（`/speckit.plan` 阶段修订）

- Q: `/speckit.plan` research 阶段核实发现，跨平台实现"真正零图标"的系统通知存在平台不对称成本——Qt 自带 `QSystemTrayIcon::showMessage()`（Widgets 模块已链接，零新依赖）在 Windows/macOS 上通常要求先有一个托盘图标实例（哪怕短暂 `show()`）才能可靠弹出通知，真正零图标需各平台分别调用原生 API（macOS `UNUserNotificationCenter` 需用户授权通知权限，Windows Toast 需 AUMID 注册，Linux D-Bus），工程代价高且三平台行为不完全一致；是否接受"统一使用 `QSystemTrayIcon`，但不再追求零图标，而是直接改为常驻图标"？ → A: 采纳常驻系统托盘图标方案（而非此前"非常驻、一次性"的决定）：使用 Qt 自带 `QSystemTrayIcon`，应用启动后创建并保持常驻显示，不再是用完即隐藏；本特性范围内仅创建最小图标（无右键菜单/无退出入口等功能集，见 Out of Scope），作为后续规划中的新功能也会需要的常驻托盘基础设施提前落地。此修订取代上一条"不新增常驻 UI"的决定，FR-005/Assumptions/Out of Scope 已据此更新。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 目标应用窗口失效时的粘贴行为明确化 (Priority: P1)

用户已通过全局热键唤起浮窗、并在其中完成了中英拼音混杂草稿到标准中文的转换；但在按下确认键（回车）之前，用户手动切换到了其他窗口、最小化或关闭了原本记录为粘贴目标的应用窗口。当用户此时按下确认键，系统需要有一种明确、可预期的行为来处理"原粘贴目标已不可用"这一状况，而不是停留在 001 遗留的未定义状态——该状态目前既可能表现为"粘贴失败但走既有统一提示"，也可能表现为"模拟粘贴被错误地发送到了当前恰好处于前台的某个无关窗口"（真正的风险场景：用户确认的内容可能被静默地注入到一个用户完全没有预期、也未被告知的窗口中）。

**Why this priority**：此场景涉及用户确认内容可能被误注入到无关窗口而不自知，属于会影响用户信任与数据去向的风险场景（判定程序 (a)/(c) 命中：改变外部可观察行为，且存在内容流向错误目的地的隐患），其严重程度高于用户故事二"按热键无反应但不知道原因"的体验问题，故设为 P1。本排序仅为内部交付次序安排（宪章原则 IV，内部细节，单行记录于此），不改变两个故事各自独立可测试、可独立交付的性质。

**Independent Test**：无需触及热键注册/冲突提示逻辑，仅通过"唤起浮窗→切换/最小化/关闭原目标窗口→确认"这一组合操作即可独立验证本故事定义的行为是否符合预期；可在不实现用户故事二的情况下独立交付。

**Acceptance Scenarios**:

1. **Given** 用户已按下全局热键唤起浮窗，系统已记录当时的目标窗口引用（`TargetFocusContext`，见 001 `data-model.md` §4），**When** 用户在按下确认键之前手动切换到其他窗口、最小化或关闭了该原目标窗口，**Then** 系统对此场景采取的具体行为遵循 FR-001 的决策结果；无论采取哪种行为，用户都能够获得与实际结果一致的明确反馈，不会出现"内容被静默注入到一个用户未预期、也未被告知的无关窗口"的情况。
2. **Given** 目标窗口在浮窗唤起期间始终保持有效且可被正常定位，**When** 用户按下确认键，**Then** 系统行为与 001 已定义的既有流程（FR-008/FR-009）完全一致，不因本特性引入任何回归或额外提示噪音。
3. **Given** 系统尝试判断目标窗口是否仍然有效，**When** 该判断本身因平台 API 限制而无法得出明确结论（既非"确认有效"也非"确认失效"），**Then** 系统 MUST 将该不确定情形与"已确认失效"同等对待，采用同一套既定降级行为，不单独定义第三种差异化处理路径。

### User Story 2 - 热键注册失败时的用户可见提示 (Priority: P2)

用户的默认全局热键 `Ctrl+Alt+Space`（macOS 对应 `Control+Option+Space`）在某些设备上会与系统本身或用户已安装的其他软件既有的快捷键发生冲突，导致应用启动时的热键注册失败。当前此情况仅被记录为内部诊断日志（`spdlog::warn`），用户完全无法从界面得知原因，只能体验到"按热键没有任何反应"，并可能误以为应用未启动、已崩溃，或自己记错了组合键。本故事要解决的是：让用户能够在这种场景下获得某种可感知的信号，从而理解"热键当前不可用"这一事实。

**Why this priority**：相比用户故事一的"内容误流向无关窗口"风险，本故事的影响范围是"功能完全不可用但用户不知道原因"，属于可用性问题而非数据去向风险，故设为 P2（内部交付次序安排，宪章原则 IV，不影响其独立可测试性）。

**Independent Test**：可通过人为制造热键注册冲突（如预先用其他程序占用默认组合键后启动本应用）来独立验证提示是否出现、以及其触发时机与承载方式是否符合 FR-005/FR-006 的决策结果；无需依赖用户故事一的实现。

**Acceptance Scenarios**:

1. **Given** 应用启动时尝试注册默认全局热键，**When** 该注册因与系统或其他已安装软件的快捷键冲突而失败，**Then** 系统 MUST 产生一种用户可感知的提示（具体承载方式见 FR-005 的决策结果），而不仅仅是内部诊断日志；用户能够据此理解"热键当前不可用"，而不是仅观察到"按键无反应"且无从查证原因。
2. **Given** 热键注册在本次启动期间已失败且提示已呈现过一次，**When** 用户在同一运行期内反复尝试按下该热键，**Then** 系统 MUST NOT 对用户造成重复、骚扰性的提示轰炸（具体节流/去重方式为内部实现细节，由实现阶段自主决定，不在本规格中定义数值或策略）。
3. **Given** 热键注册成功（未发生冲突），**When** 用户正常使用，**Then** 不产生本故事新增的任何提示，不影响 001 既有的核心体验。

### Edge Cases

- 当系统判断目标窗口是否仍然有效时，所依赖的平台原生 API 调用本身失败或超时（既非"明确有效"也非"明确失效"的第三种结果）：见 User Story 1 Acceptance Scenario 3，统一按"已失效"处理，不单独定义。
- 热键在应用运行期间反复、多次注册失败（而非仅启动时一次）：见 User Story 2 Acceptance Scenario 2，要求 MUST NOT 骚扰式重复提示，具体节流策略留待实现阶段自主决定。
- 某平台（Windows/macOS/Linux X11）不存在判断"目标窗口是否仍然有效"的可行原生 API：这是技术可行性问题而非产品决策，留待 `/speckit.plan` 的 research 阶段逐平台核实；若某平台确认不可行，该平台 MUST 保持现状行为（仍尝试执行粘贴，不新增检测逻辑），详见 Assumptions。
- 应用当前没有任何常驻的托盘图标/菜单栏 UI（001/002/003/004/005 均未实现），而热键注册失败场景下浮窗本身也无法通过热键唤起且无任何其他旁路可重新呼出（经核实 `main.cpp`/`Main.qml` 不存在 Dock 图标点击、托盘菜单或命令行二次唤起等替代路径）：本特性据此新增一个常驻系统托盘图标承载该通知，见 FR-005、Clarifications "`/speckit.plan` 阶段修订"。

## Requirements *(mandatory)*

### Functional Requirements

**用户故事一（目标应用窗口失效时的粘贴行为明确化）**：

- **FR-001**: 当用户按下确认键（回车）时，若系统判定"原目标窗口（`TargetFocusContext` 引用）在浮窗唤起期间已被用户手动切换、最小化或关闭"（含 FR-002 规定的、无法明确判断有效性的不确定情形），系统 MUST 统一降级为与 001 FR-012 一致的"已复制到剪贴板，请手动粘贴"提示，不新增任何差异化文案；系统 MUST NOT 在该场景下仍尝试执行模拟粘贴操作（见 Clarifications）。
- **FR-002**: 系统判断目标窗口是否仍然有效的能力 MUST 在 Windows/macOS/Linux X11 三个平台上的用户可感知行为保持一致；若 `/speckit.plan` 的 research 阶段核实某平台不存在可行的原生检测 API，该平台 MUST 保持现状行为（仍尝试执行粘贴，不新增检测逻辑），不得在该平台无声地产生与其他平台不一致的新行为。
- **FR-003**: FR-001 定义的降级行为 MUST NOT 改变 001 已定义的"目标窗口在确认时仍然有效"场景下的既有粘贴流程（FR-008/FR-009），仅对"目标窗口已失效"这一新增场景生效。
- **FR-004**: 系统 MUST NOT 在目标窗口已失效的场景下，产生让用户误以为粘贴已正常完成、但实际内容已静默进入一个用户未预期且未被告知的窗口的结果；用户都必须能够获知实际发生的结果（即 FR-001 所定义的"已复制到剪贴板，请手动粘贴"提示）。

**用户故事二（热键注册失败时的用户可见提示）**：

- **FR-005**: 当全局热键注册失败（含与系统或其他已安装应用已占用的快捷键冲突）时，系统 MUST 向用户提供一种用户可感知的提示，而非仅停留在现有的内部诊断日志（`SessionController::bootstrapPlatformDefaults()` 中的 `spdlog::warn`）；该提示 MUST 通过 `QSystemTrayIcon` 承载的操作系统级系统通知呈现（`QSystemTrayIcon::showMessage()`）；应用 MUST 新增一个常驻系统托盘图标作为该通知的承载基础设施（见 Clarifications "`/speckit.plan` 阶段修订"），该图标本身在本特性范围内 MUST 仅提供最小化展示能力（无右键菜单、无退出入口等额外功能，见 Out of Scope）。
- **FR-006**: 该系统通知 MUST 在应用启动、检测到热键注册失败后立即呈现（复用现有 `SessionController::bootstrapPlatformDefaults()` 中已存在的失败判断分支同步触发），MUST NOT 延后至用户实际尝试按下热键之后才被动呈现（见 Clarifications）。
- **FR-007**: 该提示所呈现的具体文案表述，本规格 MUST NOT 预先写定或自行发明（与 001 `contracts/global-hotkey-contract.md` "任何实现 MUST NOT 自行发明冲突提示文案或处理策略"的既有约束保持一致）；仅要求该提示 MUST 能让用户理解"全局热键当前不可用"这一事实，具体文案表述留待实现阶段另行确认。
- **FR-008**: 若热键在同一运行期内反复多次注册失败或被用户反复尝试触发，系统 MUST NOT 对用户产生重复、骚扰性的提示轰炸；具体的节流/去重策略属于内部实现细节，MUST 由实现阶段自主决定，不在本规格中规定具体数值或算法。
- **FR-009**: 本特性 MUST NOT 新增自定义热键绑定/修改默认组合键的配置入口；MUST NOT 新增热键冲突的自动规避或自动切换备用组合键等自愈机制（与 Out of Scope 一致，除非 `/speckit.clarify` 阶段针对 FR-005/FR-006 明确决定将此类自愈机制纳入范围）。

### Key Entities *(include if feature involves data)*

- **TargetWindowValidityOutcome**（目标窗口有效性判断结果，概念性描述）：确认（回车）时刻对 001 `data-model.md` §4 的 `TargetFocusContext` 所引用窗口进行有效性判断所得到的结果；该实体是否最终存在、其具体字段与取值集合均取决于 FR-001/FR-002 的决策结果与 research 阶段的平台可行性核实，本规格阶段不预先定义其数据结构，避免违反宪章原则 II。
- **HotkeyRegistrationNotice**（热键注册失败用户提示，概念性描述）：热键注册失败时面向用户呈现的提示所承载的状态与内容；其呈现载体、触发时机、具体文案均取决于 FR-005/FR-006/FR-007 的决策结果，本规格阶段仅记录"需要存在这样一种用户可感知的提示"这一事实，不预先定义其实现结构。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在目标窗口已于浮窗唤起期间被切换、最小化或关闭的测试场景中，100% 的验收用例里用户都能获得与实际粘贴结果一致的明确反馈，不存在"内容被静默注入到用户未预期窗口且未获任何告知"的情况。
- **SC-002**: 在目标窗口确认时仍然有效的测试场景中，本特性引入的任何新逻辑都不会造成 001 既有核心验证场景（001 `quickstart.md` 验证场景一/二/三）出现行为回归。
- **SC-003**: 在人为制造热键注册冲突的测试场景中，用户能够在尝试使用该热键后的合理时间内，获得至少一条可感知、可理解的提示，而不再仅凭"按键无反应且没有任何其他信息"来猜测原因。
- **SC-004**: 在热键注册反复失败或用户反复尝试触发的测试场景中，提示呈现的频率不会让参与验收的用户感到被骚扰或造成界面噪音干扰其正常操作。
- **SC-005**: 两类边界场景下，参与验收测试的用户均能够在事后访谈中准确复述"系统刚才发生了什么、为什么会这样"，不出现"完全没有意识到功能已失败或出现异常"的报告。

## Assumptions

- 本特性所称"热键注册失败"的触发原因（与系统或其他已安装软件的快捷键冲突、平台权限不足等）沿用 001 既有 `SessionController::bootstrapPlatformDefaults()` 诊断日志已覆盖的既有范围，不新增侦测其他新的失败原因分类。
- 本特性不改变 001 已确定的默认全局热键组合 `Ctrl+Alt+Space`（macOS 对应 `Control+Option+Space`）本身；用户仍然只能使用这一固定组合键（见 Out of Scope）。
- "目标窗口是否仍然有效"的判断在 Windows/macOS/Linux X11 各平台上的具体原生 API 可行性，是一个技术可行性问题而非产品决策，留待 `/speckit.plan` 的 research 阶段逐平台核实；若某平台的 research 结果确认不存在可行实现，该平台 MUST 保持现状（不新增检测逻辑，仍尝试执行粘贴），不视为必须在所有平台等价实现的强制要求。
- 当前应用（001/002/003/004/005 迭代至今）没有任何常驻于系统托盘或菜单栏的 UI 入口；经 FR-005 澄清（`/speckit.plan` 阶段修订），本特性新增一个常驻系统托盘图标作为通知载体，该图标本身在本特性范围内仅提供最小化展示能力，不构成对应用进行一次完整的"常驻托盘应用"改造（完整菜单/退出入口等能力见 Out of Scope）。
- Linux Wayland 桌面环境下 001 已记录的"热键注册/捕获能力不保证可用"这一既有限制（见 001 `contracts/global-hotkey-contract.md`）不在本特性讨论范围内；本特性聚焦的是"热键 API 调用本身因冲突而注册失败"这一场景，与 Wayland 环境能力限制属不同性质的问题。

## Out of Scope

- 自定义热键绑定、修改默认组合键的配置入口（001 已明确排除，MVP 不提供自定义绑定能力，本特性不推翻该边界）。
- 热键冲突的自动规避或自动切换到备用组合键等自愈机制；本特性范围仅限于"让用户能够感知到注册失败这一事实"，不涉及"系统自动尝试其他组合键"这类更复杂的自愈能力，除非 `/speckit.clarify` 阶段针对 FR-005/FR-006 明确决定纳入。
- 深度诊断"具体是哪一个第三方软件占用了该快捷键"的能力；本特性最多只要求用户能够感知"当前默认热键注册失败"这一事实，不要求系统枚举或定位具体的冲突来源。
- "目标窗口是否仍然有效"判断的具体技术实现方案（平台 API 选型、调用方式）；具体选型留待 `/speckit.plan`/research 阶段确定，本规格仅定义外部可观察行为层面的决策分歧点。
- 操作系统级系统通知的外观样式、用户通知权限授予流程、"勿扰模式"等系统级通知管理设置均为平台原生能力，不在本特性范围内；本特性仅要求触发一次该系统通知调用，不涉及对通知内容样式的定制化实现。
- 常驻系统托盘图标的完整功能集（如完整右键菜单、从中退出应用、显示应用运行状态等）不在本特性范围内；本特性仅要求创建该图标并承载 FR-005 的通知能力，图标本身的后续功能扩展留待未来特性另行规划（见 Clarifications "`/speckit.plan` 阶段修订"）。
